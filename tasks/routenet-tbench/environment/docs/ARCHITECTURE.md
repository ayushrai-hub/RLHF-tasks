# Architecture

This is a small Node.js project that trains a link-prediction model on a
route-network graph. The graph is stored in PostgreSQL and the model is built
with TensorFlow.js. All three stages run in a single container.

## Data flow

```
PostgreSQL  -->  src/lib/db.js  -->  src/lib/sampler.js  -->  src/cli/train.js
                                            |
                                            v
                                src/lib/graph.js   (graph utilities)
                                src/lib/model.js   (TF.js model)
                                src/lib/metrics.js (AUC, hit-rate, etc.)
```

The trainer pulls positive edges from `routenet.edges` (filtered to the train
split) directly from Postgres. The sampler is responsible for producing the
negative examples that pair with those positives.

Historically the sampler read a denormalised snapshot of the graph from disk
(`data/snapshot.json`) so it did not have to round-trip to the database for
every training step. The snapshot was regenerated by hand whenever the schema
changed. That worked while the train/val/test split was stable, but the split
has since been adjusted and the snapshot has not been regenerated.

## Module responsibilities

- `src/lib/db.js` - thin wrapper around `pg.Client`. Reads `config/db.json`,
  exposes `connect()`, `disconnect()`, `query(sql, params)`, and a couple of
  convenience helpers for fetching edges by split.
- `src/lib/graph.js` - in-memory graph representation built from an edge list.
  Provides BFS-based shortest-path queries.
- `src/lib/sampler.js` - the hard-negative sampler. This is the module that
  the current task focuses on.
- `src/lib/model.js` - link-prediction head over learned node embeddings,
  implemented with `@tensorflow/tfjs`.
- `src/lib/metrics.js` - AUC and related metrics computed from logits and
  labels.
- `src/lib/util.js` - small helpers: argv parsing, deterministic PRNG,
  pair canonicalisation, etc.
- `src/cli/sample.js` - CLI shim around `sampler.js`; writes a JSON file.
- `src/cli/train.js` - CLI shim around the trainer; reads the sampler output,
  trains the model, prints validation AUC.

## Hard negatives

A negative example is an unordered pair of nodes `(u, v)` that the model
should learn to distinguish from a real edge. Two design choices matter:

1. **Source of truth for edges.** The model is trained on what is currently in
   Postgres. Negatives must respect the same snapshot of the graph, otherwise
   validation edges leak into the negative set and the AUC measurement is
   biased.

2. **Difficulty.** Random negatives are too easy. We want negatives that are
   "close" to positives in the graph - specifically, pairs whose shortest-path
   distance in the **train subgraph** is **2 or 3 hops** (`MIN_HOPS` /
   `MAX_HOPS` in `config/sampler.json`) but that are not themselves edges in
   any split. Pairs at distance 1 are train edges; pairs beyond distance 3 are
   too easy to distinguish. This forces the model to learn structural features
   instead of memorising neighbourhood blobs.

See `SCHEMA.md` for the database schema and the split convention, and
`AUDIT.md` for the rules the sampler source has to obey.
