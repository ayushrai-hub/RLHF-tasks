Repair the authorization-cache simulator under /app/environment. The simulator models the identity cache, the group indexing data structure, the directory snapshots with freshness, the revisions data structure, the resume data structure, and the update journal for the cache. Revoked rights within a given directory must disappear from the freshness bound of that directory. Resumed runs of the authorization server must exhibit the same behavior as monolithic runs of the authorization server. Users that have valid rights to perform an action must be able to go through the normal authorization workflow.

There are several durable surfaces within the simulator. Fixing one issue can reveal another issue in the documented authorization workflow.

Build the simulator with the command make -C /app/environment build. The compiled executable is `/app/environment/bin/authzctl`, which must satisfy the documented `run-case` contract in `/app/environment/docs/operator-contract.md`, `/app/environment/docs/scenario-format.md`, `/app/environment/docs/cache-state.md`, and `/app/environment/docs/trace-schema.md`. The output of the simulator will be written into the file `/app/output/authorization-trace.json`, which will contain the fields schema_version, directory_revision, proof_revision, and any additional fields that are part of the public contract of the authorization simulator, as is documented in trace-schema.md.

The static and manual ways of providing the simulator output are insufficient to provide a valid repair. Editing the static JSON files, providing wrappers around the executable, editing the harness, purging the cache, editing the state files directly, writing handwritten traces, and providing hardcoded answers are all insufficient repair strategies. The authorization checker will delete the outputs directory, rebuild the application from source, and re-run generated `authzctl run-case` scenarios. The Go source code under `/app/environment` must be fixed and rebuilt; output-only work is not sufficient.
