# Authorization trace schema

The output trace is JSON with `schema_version: 1` and these top-level fields: `case`, `freshness_bound`, `refreshes`, `decisions`, `cache_entries`, `group_index`, `audit`, and `provenance`.

`refreshes` records include `step`, `tick`, `revision`, `proof_revision`, `proof_age`, `accepted`, and `reason`. A refresh is accepted only when the proof revision equals the snapshot revision and the proof age is within the scenario bound at the refresh tick.

`decisions` records include `step`, `tick`, `username`, `subject_id`, `resource`, `action`, `result`, `reason`, `required_groups`, `groups`, `directory_revision`, `cache_revision`, `proof_revision`, `proof_age`, and `generation`. `result` is `allow` or `deny`. A decision can allow only from a non-revoked cache entry whose cache revision and proof revision match the active directory revision, whose `refresh_epoch` matches the runner's current refresh-epoch counter (see `cache-state.md`), whose subject id and generation match the active directory principal for that username, whose proof age is within the freshness bound at the authorize tick, and whose groups include at least one required group.

`cache_entries` and `group_index` are the final local state snapshot after the scenario steps. They must be coherent with accepted refreshes and decisions, and with the on-disk `cache_entries.json` and `group_index.json` written under the state directory. After a rejected refresh, `group_index` must not retain username-keyed membership that would grant authority from an earlier accepted refresh; the persisted `group_index.json` must match that fail-closed outcome. Each `cache_entries` row includes `username`, `subject_id`, `generation`, `groups`, `revoked`, `refreshed_at`, `refresh_epoch`, and revision fields. `refresh_epoch` follows the counter rules in `cache-state.md`. Slice-valued fields such as `groups` serialize as JSON arrays; empty collections use `[]`, not `null`. `provenance` includes a deterministic `case_digest` over the scenario file, the output path the trace was written to, and a `resume` object with `used`, `from_step`, and `epoch_start`. For resumed runs, `epoch_start` is the refresh-epoch counter loaded at the resume boundary (after any reconciliation with cache entries), not the counter after the resumed segment completes.

The provenance digest algorithm is sha256 over the exact scenario file bytes. The provenance object contains `generated_by`, `case_digest`, `output_path`, and `resume`. Fixture and operator scenarios may use ordinary group labels such as `ops`, `staff`, `rooters`, `readers`, `finance`, and `dev`, and resource ids such as `resource`, `vault`, `desk`, `ledger`, `cluster`, `archive`, and `payroll`; these are data values carried through `groups`, `required_groups`, `group_index`, and authorization decisions, not hardcoded policy names.

Refresh `accepted` is the JSON boolean `true` when the proof is authoritative and `false` when it is not. The canonical authorization denial reasons include `proof-revision-mismatch` for a refresh proof that names another revision, `unproven-directory-revision` for an authorization attempted against a cache entry whose proof/revision does not match the active directory revision, `stale-cache-epoch` when the entry was not produced by the latest accepted refresh, `subject-generation-mismatch` when the cached subject no longer matches the active directory principal for that username, `proof-expired-at-authorize` when the proof is too old at the authorize tick even if the refresh tick was inside the bound, and `revoked-principal` when the cache entry is marked revoked (including principals absent from the active snapshot after refresh).

`subject-generation-mismatch` applies only when the username is still present in the active directory snapshot. When a principal is missing from the active snapshot and the corresponding cache row is revoked, authorization must deny with `revoked-principal`, not `subject-generation-mismatch`.
