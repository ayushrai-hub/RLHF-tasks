The change-request approval service under /app/src builds and boots fine, but it's been routing requests wrong and the platform team keeps reopening tickets. It's a small in-memory Go REST API where each change request carries a title, an author, and an ordered list of approval stages, and it tracks the decisions approvers record against it. The request and response shapes are already defined by the handlers, store and models under /app/src — read them for the exact JSON contract. Don't change the contract; make the behavior correct.

The core idea: a change request walks its stages in order. A stage is satisfied once at least `required` distinct eligible approvers have approved it (so `required` is a quorum — two distinct people when required is 2, not one person twice), and only then does the next stage open. The first stage that isn't yet satisfied is the request's current stage, and decisions may only be recorded for that current stage. When every stage is satisfied the request is approved, and its current stage then reads as the stage count — i.e. the index one past the last stage. A reject recorded at the current stage rejects the whole request immediately and is terminal; once a request is approved, rejected, or canceled, no new approve/reject decision is accepted. Revoking is different — it withdraws an existing decision rather than recording a new one, so it stays available even after a request has become approved; only a canceled request refuses a revoke. Revoking withdraws that approver's most recent active decision, and if that drops an already-satisfied earlier stage back below quorum the request rolls back to that stage — and an already-approved request is itself rolled back out of the approved state when the revoke pulls a satisfied stage below quorum. Every decision that had been recorded for later stages is then discarded, so the request cannot vault forward again on stale approvals. Editing a request (its title or its stages) discards all recorded decisions, sends it back to the first stage, and bumps a content `revision` counter that is separate from the optimistic-concurrency `version`. Baseline matters here: a newly-created request starts at `revision` 0 and `version` 1, and the two counters move independently — every successful edit increments `revision` by 1 (so the first edit makes it 1), while `version` increments on every version-bearing mutation (edit, cancel, revoke). Do not initialize `revision` to 1 and do not tie it to `version`.

There are also reusable approver groups under /groups: a group is a named roster of members, and a stage can name groups in `eligible_groups` instead of (or in addition to) listing approvers literally. A stage's effective eligible set is the literal `eligible` ids unioned with the current members of every group it references, resolved live — so editing a group's membership immediately re-routes every request that references it. If removing a member drops an already-satisfied stage back below quorum, that request must be seen as pending again the very next time it's read (its cached view can't go stale). A stage that references a group that doesn't exist is a 422, and "distinct eligible approvers" for the unsatisfiable check counts that effective union. Groups can be created, listed, fetched, edited and deleted; editing a group takes an If-Match (428 missing / 412 stale) and bumps the group's version; a group that is still referenced by any request cannot be deleted (409); /stats also reports a lifetime count of groups created that survives deletion.

Specific things that should hold:
- Creating a request requires a non-empty title and author and at least one stage; every stage needs a name, a `required` of at least 1, a non-empty effective eligible set, and a `required` no larger than the number of distinct effective-eligible approvers (an unsatisfiable stage is a 422). Creating a group requires a non-empty name and at least one member.
- Recording a decision rejects an ineligible approver (422), a second decision from someone who already decided the current stage (409), and a decision other than "approve" or "reject" (422).
- Listing supports 1-based pagination (default page size 20) where the first page starts at the very first record and consecutive pages never overlap; `total` is the count of all matches, not just the returned page; an empty result is a JSON array, never null. There's an optional `status` filter and a `sort` option — read the code for the keys.
- A per-approver rollup at /approvers/{id} reports the approver's currently-active approvals versus a lifetime count of approvals they've ever given (which must not drop when a decision is revoked or its request deleted), plus the requests currently waiting on them at their current stage.
- /stats counts lifetime requests created (this survives deletion), the number of currently-active (non-terminal) requests, lifetime approvals recorded, and lifetime revokes processed.
- Editing, canceling, and revoking require an If-Match header carrying the current version: missing it is 428, a stale value is 412, and reads and successful mutations return the current version in an ETag. Bodies on writes must be `application/json` (else 415) and must not carry unknown fields (else 400). Wrong methods return 405 with an Allow header.
- The service is hit concurrently and must stay race-free — it has to be clean under the Go race detector while reads and writes run at the same time.
