# Repair weather, current, duration, and scoring policy

Weather windows live in /app/data/weather/windows.csv. A span can use a window only when the window region equals the span region, the ship is available no later than the window start, the ship max sea state is at least the window max sea state, and the corridor current for that window does not exceed the window current_limit_mps. Ship availability and window timestamps are ISO-like UTC strings and compare lexicographically.

The C drift helper built by /app/scripts/run_glassreef_planner.sh is authoritative for drift scoring. The planner should use /app/build/current_adjust with mean_mps, bearing_deg, and depth_m; do not duplicate the helper formula inside the planner. The helper's integer result contributes to score but does not by itself reject a repair.

The C duration helper /app/build/repair_duration is authoritative for repair length. The planner should pass span length_nm to it, treat the returned integer as duration hours, schedule a candidate from the weather window start, and set the repair end_utc to start_utc plus that duration. A candidate is usable only when this computed end_utc is no later than the weather window end_utc. Duration failures are reported with reason no-duration-window when depth, splice, weather, and current conditions had at least one otherwise usable option.

Mission constraints live in /app/data/missions/glassreef_primary.json. ship_cooldown_hours is the minimum gap after a ship's actual computed repair end before that same ship may start another repair. ship_blackouts lists ship_id, start_utc, and end_utc intervals; a candidate is invalid when its actual repair interval overlaps a blackout for that ship. Blackout-only failures are reported with reason ship-blackout. Ship schedule conflicts include overlap with earlier scheduled repairs or violation of the cooldown gap. Intervals are start-inclusive and end-exclusive, so one interval ending at a timestamp does not overlap another starting at that timestamp, but cooldown still applies after the earlier end.

The hazard penalty for a span is floor(total severity for hazard JSON records in /app/data/reference/hazards whose region equals the span region / 100). Invalid hazard JSON files or hazard records without a region or numeric severity are ignored. The repair score is priority_base * 10 + restored_priority + compatibility_bonus + crew_bonus - drift_penalty - depth_penalty - hazard_penalty. Crew bonuses are A=8, B=4, C=1, otherwise 0. depth_penalty is 0 through 3000m and floor((depth_m - 3000) / 700) after that.

Candidate repairs are ranked by descending score, then start_utc, ship_id, and span_id. Broken spans are scheduled greedily by their best candidate using descending best score, then best start_utc, then span_id.
