The bell team has been planning the August rota by hand, and the spreadsheet is starting to miss conflicts. Please put a small command line planner at `/app/carillon-planner`; it should read an input JSON path and an output JSON path, for example:

`/app/carillon-planner /app/input/august_rota_requests.json /app/output/plan.json`

Treat `/app/input/august_rota_requests.json` as read-only source data. The input JSON has `towers`, `ringers`, `existing_sessions`, `maintenance`, and `proposals`. Tower rows are `{id: string, bells: int, methods: [string], max_minutes: int}`. Ringers are `{name: string, tier: "novice"|"competent"|"experienced"|"conductor", max_minutes: int}`. Existing sessions are `{id, tower, start, end, status, ringers}` and only `"scheduled"` sessions block time. Maintenance rows are `{tower, start, end, kind}` and only `"hard"` maintenance blocks time. Proposals are `{id, tower, method, start, end, score, mandatory, assignments}` with assignment rows `{bell, ringer}`. All times are UTC strings ending in `Z`; string ordering is enough. Intervals are half-open `[start, end)`, so sessions that only touch at an endpoint are not overlapping.

Evaluate each proposal with this first-failure order: missing tower, unsupported method, `end <= start`, bells are not exactly `1..tower.bells`, unknown ringer, same ringer assigned twice, tier too low for the bell, hard maintenance overlap, scheduled session in the same tower, scheduled session using an assigned ringer. The reason strings are exactly `tower_unknown`, `method_unsupported`, `bad_interval`, `bad_assignments`, `ringer_unknown`, `duplicate_ringer`, `tier_mismatch`, `maintenance`, `tower_busy`, and `ringer_busy`. Bell rules are: bells `<= N/2` allow any tier, bells `N/2 < bell < N` need at least `competent`, and bell `N` needs at least `experienced`.

After that, choose the sessions to run. Every usable `mandatory=true` proposal must be selected. Selected proposals cannot overlap in the same tower, cannot overlap if they share a ringer, and shared ringers need at least 30 minutes between sessions even when the intervals do not overlap. The total selected minutes for a tower must not exceed that tower's `max_minutes`; the total selected minutes for a ringer must not exceed that ringer's `max_minutes`. Existing sessions do not count toward those minute caps, but selected mandatory sessions do. If the usable mandatory proposals cannot coexist under the overlap, rest, or minute-cap rules, write `status: "infeasible"` with no selected sessions. Otherwise write `status: "ok"` and choose the compatible set that includes the usable mandatory proposals and maximizes total score. Break ties by selecting more proposals, then by smaller total scheduled minutes, then by the lexicographically smaller comma-joined selected ids. Those tie-breaks compare the complete selected set, not one local candidate at a time.

Write JSON to the output path as `{status, selected, rejected, total_score}`. The checker compares the parsed JSON value, so field names, strings, and array contents need to match this contract. `status` is `"ok"` or `"infeasible"`, `total_score` is an integer, `selected` is sorted by proposal id and each row is `{id, tower, start, end, score, ringers}` with `ringers` listed by ascending bell number. `rejected` keeps the original proposal order and each row is `{id, reason}`. Each rejected proposal gets exactly one reason: failed proposals keep the first validation reason above, while a usable optional proposal left out of the winning set, including one left out because of a tower or ringer minute cap, uses `conflicts_with_selected`. In the mandatory-conflict case, usable mandatory proposals use `mandatory_conflict`, other usable proposals use `blocked_by_mandatory_conflict`, and proposals that failed their own validation keep their original reason. Empty arrays are valid.

The real rota export can have up to 45 proposals, 8 towers, and 30 ringers, so the planner still needs to return the exact best plan for that size.
