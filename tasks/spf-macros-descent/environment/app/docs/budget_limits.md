# budget-limits

The evaluator maintains two per-message counters, lookups and void_lookups, both starting at zero when a message begins. These are shared across all recursive descents made while evaluating that one message; an include or redirect never gets a fresh budget. Both counters are read from /app/data/policy.json under the keys max_lookups and max_void_lookups. A third policy key, max_redirect_hops, bounds how many redirect chains one message may follow (see below).

Every distinct DNS query made during evaluation increments lookups by one, UNLESS the same (name, rtype) pair has already been queried during evaluation of this SAME message — in which case the second query is served from the in-eval memo without incrementing either counter. The memo key is (lower-cased-name, rtype), where rtype is exactly one of "A", "AAAA", "MX", or "TXT"; different rtypes on the same name are separate memo entries. Query kinds that increment lookups (on the first ever request only): the initial TXT lookup for the sender's own domain, the TXT lookup on any include or redirect target, the A lookup for an a mechanism (which also covers AAAA if the target has both — an a mechanism performs one logical lookup that returns the union of A and AAAA), the MX lookup for an mx mechanism, each per-exchanger A lookup that follows an mx lookup (each exchanger is a separate name and thus a separate memo entry), and the A lookup for an exists mechanism. If the increment brings lookups above max_lookups, the current message's verdict is immediately "permerror" and evaluation stops; the mechanism field is the empty string, and the lookups counter reflects the count including the one that triggered the overflow. The initial TXT lookup for the sender's own domain counts even when the verdict ends up being "none" because the record was absent.

The memo is important for the void counter too. A void lookup is one whose response contains no records of the relevant type. Concretely: an A lookup on a name that is not present in dns.json, or is present but has no "A" and no "AAAA" list, is void; likewise an MX lookup that returns no exchangers is void; an exists A lookup on a name with no A records is void; and a TXT lookup on a name that is not present, or has no TXT list, or has a TXT list but no entry starting with "v=spf1", is void. Void lookups increment BOTH lookups and void_lookups on the FIRST-ever request only; a memoized re-lookup for the same (name, rtype) does not double-count the void. If the FIRST increment brings void_lookups above max_void_lookups, the message immediately becomes "permerror" with the counters reflecting the void that triggered it. This is a single global budget for the message; a void triggered inside a deeply nested include still counts toward the same total the outer walk sees, and the same is true across a redirect. There is no per-recursion window and no separate outer/inner counter.

The initial TXT lookup on the sender's own domain, when it returns no v=spf1 record, is a void lookup by the criteria above. It counts toward both budgets like any other, but the verdict is still "none" in the void cases where the domain has no record; only later voids beyond max_void_lookups escalate to permerror. If the very first TXT lookup itself overflows max_void_lookups (max_void_lookups=0 is a legal, if unusual, setting), the verdict is "permerror".

Include and redirect never reset either counter. When include:X is evaluated, the recursive walk on X is entered with the current counter values and the current memo, mutates them as it goes, and returns them unchanged to the caller; the caller then continues consuming budget from that shared state. This global-budget rule is the intended reading of the two limits: a slightly bloated include chain plus one void lookup in the outer record can overflow even though neither the outer walk nor the inner include would exceed a per-scope limit on its own. The memo is also shared globally within one message, which means a domain X that voided during evaluation of one include is remembered as void when a sibling include later re-references X — the sibling does NOT incur a second void lookup, but the memo delivers the same void status.

Two loop guards operate ON TOP of the numeric budgets and can trigger permerror before the numeric budget would. First, redirect loop guard: the evaluator maintains a set of domains it has entered via redirect during this one message. If a redirect target names a domain that is already in that set, the verdict is immediately "permerror" (no further evaluation). The starting-domain evaluation is NOT considered a redirect entry; only actual "redirect=" traversals count. Second, include recursion depth guard: the recursion depth via include is bounded by max_redirect_hops from policy.json (the same number is reused for both bounds); an include descent that would exceed depth max_redirect_hops is "permerror". Both loop guards produce permerror with mechanism="" and preserve the counters exactly as they stood when the guard fired (no phantom lookup increment).
