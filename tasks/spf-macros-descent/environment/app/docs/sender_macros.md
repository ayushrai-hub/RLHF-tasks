# sender-macros descent

This is the contract for the spf-trace program. It reads an envelope journal at /app/data/messages.jsonl one message per line, evaluates the sender's SPF policy against the offline DNS snapshot at /app/data/dns.json under the budgets in /app/data/policy.json, and writes /app/output/verdicts.ndjson (one line per input message, same order) plus /app/output/summary.json.

Each message carries id, mail_from (the RFC 5321 envelope sender), helo, and from_ip. The sender's domain is the substring of mail_from after the last @, lowercased. Its SPF record is found by looking up the TXT record set for that domain and scanning the returned entries for exactly one that begins with the prefix "v=spf1" (followed by either a space or end-of-string). If exactly one such entry exists, it is the SPF record. If zero such entries exist (the domain has TXT records but none matches, or the domain is absent from the DNS snapshot), the verdict is "none" and the trace has a single entry "eval:<domain>"; when the domain is absent that TXT lookup is a void lookup per the budgets doc. If two or more entries in the same TXT rrset each begin with "v=spf1", the record is treated as permerror — RFC 7208 §4.5 forbids multiple SPF records at the same name, and a naive reader who picks "the first one" and marches on will land in the wrong verdict for every message from such a sender.

The record body is the text after the "v=spf1" prefix, split on ASCII whitespace into terms. A term is either a mechanism or a modifier. Modifiers are of the form "name=value"; only "redirect=" and "exp=" are recognized names — "exp=" is silently ignored, "redirect=" is honored, and any other modifier name (or a mechanism-shaped term whose first token contains "=") is a permerror. Mechanisms are optionally prefixed with a qualifier of "+", "-", "~", or "?" defaulting to "+". Names accepted are all, ip4, ip6, a, mx, include, exists.

A mechanism matches according to its type; a matching mechanism ends the walk and its qualifier decides the verdict: "+" produces "pass", "-" produces "fail", "~" produces "softfail", "?" produces "neutral". If no mechanism matches, the record's modifiers decide the outcome. If a "redirect=" modifier is present AND no mechanism named "all" (with any qualifier) appears in the same record, the redirect target is evaluated as if it were the sender's domain, and its verdict is returned (with the outer's lookup budget). If both redirect and all are present in the same record, redirect is ignored. If neither redirect fires nor any mechanism matches, the verdict is "neutral".

The all mechanism always matches. The ip4:CIDR and ip6:CIDR forms match when from_ip is inside the CIDR block; a bare "ip4:x.x.x.x" or "ip6:X:X::X" (no slash) matches exact equality within the same family. Cross-family comparisons never match. Important family rule: an IPv4-mapped IPv6 address (an IPv6 literal of the form ::ffff:a.b.c.d, or the equivalent hex ::ffff:X:X, whose upper 96 bits are zero except for one 0xffff word) is treated as IPv4 for the purpose of family matching — an ip4 mechanism CAN match it and an ip6 mechanism NEVER matches it. Non-mapped IPv6 addresses only match ip6 mechanisms. The a mechanism takes an optional target domain and an optional "/N" CIDR length. With no target, the current evaluating domain is used. It performs a single A lookup on the target and matches from_ip against each returned address (using the CIDR length if given, else exact address equality). The mx mechanism performs an MX lookup on the target, sorts the returned exchangers by ascending preference, then performs one A lookup per exchanger and matches from_ip against the union of those addresses in the same style. The include:DOMAIN mechanism evaluates DOMAIN's SPF policy recursively and the include mechanism matches only when the recursive verdict is exactly "pass"; a recursive "fail", "softfail", or "neutral" causes the include to not match and the walk to continue; a recursive "none" upgrades to "permerror"; a recursive "permerror" or "temperror" propagates unchanged. The exists:DOMAIN-SPEC mechanism performs an A lookup on the macro-expanded DOMAIN-SPEC and matches when at least one A record is returned.

Domain-spec arguments to include, exists, a, mx, and redirect are subject to macro expansion. A macro token is written "%{X <digits?> <r?> <delim-chars?>}" where X is one letter (see below), the optional digits are a positive decimal count (the "keep the rightmost N labels" trimmer), the optional "r" flag (case-insensitive) reverses the label order, and the optional trailing delimiter characters replace the default label-split delimiter set for THIS macro only. The default label-split delimiter set is the single character ".". If any delimiter characters appear between the "r" flag (or the digits if no "r") and the closing brace, they define an alternate delimiter set: every character in that trailing tail is a valid label separator for the split step. Example: "%{s+_.}" on mail_from "alice+news@sender-a.test" splits the raw string on any of "+", "_", or "." (yielding ["alice", "news@sender-a", "test"]) before trimming and rejoining; the rejoin uses "." as the single output separator regardless of what the input delimiter set was. Order inside the braces is fixed: letter, optional digits, optional r, optional delimiter tail — anything out of order is a permerror. The letters supported are s (mail_from), l (local part of mail_from), o (domain part of mail_from), d (current evaluating domain), i (envelope IP; for IPv4 the dotted-quad, for IPv6 the fully expanded 32-nibble form joined by dots), h (helo), r (receiving domain from policy.json). Outside of "%{...}", the sequences "%%" produce "%", "%_" produce a single space, and "%-" produce the three characters "%20"; any other "%X" is a permerror. Note that the nibble expansion for IPv6 is what makes reverse lookups of IPv6 addresses tractable; a raw compressed form is never used inside a macro-expanded name.

Verdicts on each message are written as one JSON object per line to verdicts.ndjson with fields id, result, mechanism, domain, lookups, void_lookups, and trace. The mechanism field is a strictly-defined string with the following grammar. For a mechanism-matched verdict, mechanism is the qualifier character (always the effective qualifier: "+" if the mechanism had no explicit qualifier, "+", "-", "~", or "?" otherwise) followed by the ORIGINAL UNEXPANDED mechanism token as it appeared in the record body (macros stay as literal "%{X...}" fragments; the pre-macro-expansion form of the token is what appears here — including any "/N" CIDR suffix). For a redirect-resolved verdict (the outer walk fell through to a redirect that returned pass/fail/softfail/neutral), mechanism is the literal string "redirect=" followed by the fully MACRO-EXPANDED target domain that the redirect chained to (the innermost redirect target actually evaluated, if redirect chained). For "none", "neutral" from fall-through, "permerror", and "temperror" verdicts, mechanism is the empty string. The domain field is the initial evaluating domain (lowercased). lookups and void_lookups are the final counters (see the budgets doc). trace is an ordered list of evaluation events: each recursive descent adds "eval:<lower-cased-domain>" when it starts, and the terminal matching mechanism string is appended when a mechanism matches (using the same qualifier-plus-unexpanded-token grammar as the mechanism field). summary.json contains total (an integer count of messages processed), counts (an object mapping each of pass, fail, softfail, neutral, none, permerror, temperror to the integer count for that verdict class in verdicts.ndjson), and chain_digest (see /app/docs/chain_digest.md); it must be pretty-printed with a two-space indent and a trailing newline, and the keys must appear in the order total, counts, chain_digest.

Worked example one — exists with a macro: consider a message with id "wx1", mail_from "eve@sender-e.test", from_ip "198.51.100.5", where sender-e.test's SPF record is "v=spf1 exists:%{ir}.rbl.example.test ip4:198.51.100.0/24 -all". The macro %{ir} splits the raw IPv4 "198.51.100.5" on "." (default delimiter), reverses to ["5","100","51","198"], and rejoins to "5.100.51.198". The A lookup on "5.100.51.198.rbl.example.test" returns a record, so the exists mechanism matches with its effective + qualifier. The mechanism field is EXACTLY "+exists:%{ir}.rbl.example.test" — the macro %{ir} stays as its unexpanded three-character token; the expanded target "5.100.51.198.rbl.example.test" does NOT appear here. The trace's terminal entry is also "+exists:%{ir}.rbl.example.test" (unexpanded), while the recursive-descent events that led here record only "eval:sender-e.test".

Worked example two — redirect resolution: consider a message with id "wx2", mail_from "bob@sender-b.test", from_ip "192.0.2.130". sender-b.test's TXT record is "v=spf1 redirect=_spf.shared.test" and _spf.shared.test's is "v=spf1 ip4:192.0.2.128/26 -all". The outer walk has no matching mechanisms and no "all", so the redirect fires; _spf.shared.test evaluates to pass via +ip4:192.0.2.128/26. The verdict's mechanism field is EXACTLY "redirect=_spf.shared.test" — the outer redirect target, not the inner "+ip4:192.0.2.128/26" mechanism string. The inner mechanism string DOES appear in the trace as the terminal event, but the top-level mechanism field is the redirect target. The trace is ["eval:sender-b.test", "eval:_spf.shared.test", "+ip4:192.0.2.128/26"]; lookups=2, void_lookups=0.

A short self-check pair is provided: /app/data/sample_in.jsonl with three simple messages and /app/data/sample_out.ndjson with the expected verdicts for those three (base mechanics only — the sample deliberately does NOT exercise macros, custom delimiters, multi-TXT concatenation, IPv4-mapped IPv6, memoization, redirect loop guard, or chain_digest). Running the built program on the sample must reproduce sample_out.ndjson byte for byte before running against the full messages fixture. To make this practical the program reads its input directory from the environment variable SPF_DATA_DIR (falling back to /app/data when the variable is unset or empty) and its output directory from SPF_OUT_DIR (falling back to /app/output). This override applies uniformly to dns.json, messages.jsonl, policy.json, and the two output files; the docs directory is always at /app/docs and is not overridden.
