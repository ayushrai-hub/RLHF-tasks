> migration. The lore is long and the lantern-oil is short; the load-bearing
> rules are gathered into the four Appendices at the end. Everything between is
> the wardens' own account, kept here so that nothing of the vault's temper is
> lost. Read the Appendices to migrate the archive; read the chapters to know
> what you are migrating.

# Appendix I -- The Cartographer's Normalisation Contract

Before any vault may be migrated, the four sources of the season-archive must be
read and *normalised* into a single canonical schema report. The four sources are:

* `rooms.csv` -- a comma-separated table of chambers (its header is written in the
  old PascalCase hand: `RoomId,Name,Depth,Biome`).
* `monsters.parquet` -- an Apache Parquet table of the vault's guardians, columns
  `monster_id, room_id, species, base_hp, base_atk`.
* `relics.json` -- a JSON array of relic records whose keys are written in the
  scribe's camelCase hand: `relicId, roomId, name, baseValue, sigil`.
* `tiles/` -- one ASCII tile map per chamber, named `room_<room_id>.txt`.

**Rule I.1 (column names).** Every column or key is rewritten into `snake_case`.
A capital letter that begins a word is lowered and prefixed with an underscore
(except at the very start of the name): `RoomId -> room_id`, `baseValue ->
base_value`, `relicId -> relic_id`. Names already in snake_case are unchanged.

**Rule I.2 (dtypes).** Each normalised column has exactly one canonical dtype.
A column is `"int"` if **every** value in it is a whole number; otherwise it is
`"str"`. There are no floating-point columns anywhere in the archive.
**Exception:** any column whose normalised name ends in `_id` (`room_id`,
`monster_id`, `relic_id`, ...) is a *catalogue identifier* and is **always**
recorded as `"str"`, even when every one of its values is a whole number. (The
binder treats catalogue marks as opaque text, never as arithmetic quantities.)

**Rule I.3 (the tiles table).** The `tiles/` directory is normalised into a
two-column table named `tiles` with columns `room_id` and `hazard_count`, one row
per `room_<room_id>.txt` file. The `hazard_count` of a chamber is the number of
spike glyphs `^` that appear in its tile map (every other glyph is ignored).

**Rule I.4 (per-table fingerprint).** Each table is reduced to a SHA-256
fingerprint computed as follows:

1. Order the table's columns **alphabetically** by their normalised name.
2. Sort the rows **ascending by primary key**. The primary keys are: `room_id`
   for `rooms`, `monster_id` for `monsters`, `relic_id` for `relics`, and
   `room_id` for `tiles`.
3. Render each row as the string `col=value` for every **non-key** column, in the
   alphabetical column order, joined with a single pipe `|`. The **primary-key
   column is OMITTED** from the row string -- it is used only to order the rows in
   step 2, never hashed (the digest attests a row's *contents*, not its catalogue
   number). Integers are rendered as their base-ten digits; strings are rendered
   exactly as stored.
4. Join the row strings with a single newline `\n` (no trailing newline) and take
   the SHA-256 hash of the UTF-8 bytes. The fingerprint is the lowercase hex digest.

**Rule I.5 (the schema report).** The report is a JSON object whose keys are the
four table names `monsters`, `relics`, `rooms`, `tiles`. Each maps to an object
with keys `columns` (the alphabetically ordered normalised names), `dtypes` (the
canonical dtype of each column, in the same order), `row_count` (an integer), and
`fingerprint` (the hex digest of Rule I.4). The report is serialised with
`json.dumps(report, sort_keys=True, indent=2)` followed by a single trailing
newline, and written to `/app/out/schema_report.json`.


# Appendix II -- The Wardens' Ledger (derivation of chamber statistics)

The migrated database describes the vault as an ordered sequence of *chambers*.
The chambers are ordered by `depth` **ascending**; the shallowest chamber is
`chamber_index` 0, the next is 1, and so on. (Depth is not the same as room id --
the cartographers re-sounded the vault every season.)

**Rule II.0 (depth ties).** When two or more chambers share the same `depth`,
they are ordered among themselves by `room_id` **descending** -- the
higher-numbered room takes the earlier (shallower) `chamber_index`. This is the
only tie-break: it is *not* the archive's input order and *not* `room_id`
ascending. (Depths are frequently distinct, so this rule bites only when the
re-sounding left two chambers at the same depth.)

Each chamber draws a biome from its room. The biome grants three modifiers, set
down here as the Wardens' Ledger:

| biome   | hp_bonus | atk_bonus | worth_multiplier |
|---------|----------|-----------|------------------|
| crypt   | +3       | +0        | x1               |
| forge   | +0       | +2        | x2               |
| mire    | +5       | +1        | x1               |
| vault   | +1       | +1        | x3               |

**Rule II.1 (the guardian).** A chamber's guardian is the **selected** candidate
guardian for the chamber's room (a room may list several candidates -- see Rule
II.3). If a chamber has a guardian, then

* `guard_hp  = base_hp  + biome.hp_bonus + 2 x hazard_count`
* `guard_atk = base_atk + biome.atk_bonus + (hazard_count // 2)`

where `hazard_count` is the spike count from Rule I.3 and `//` is integer
(floor) division. The spikes raise **both** the guardian's hit points *and* its
attack: every full pair of spikes lends one extra point of `guard_atk`. If a
chamber has **no** guardian, both `guard_hp` and `guard_atk` are `0` and its
species is `none`.

**Rule II.2 (the relic).** A chamber's relic is the **selected** candidate relic
for the chamber's room (Rule II.3). If a chamber holds a relic, then

* `relic_worth = max(0, (base_value - hazard_count) x biome.worth_multiplier)`

The spikes mar the relic **before** the biome's worth multiplier is applied: the
`hazard_count` is subtracted from `base_value` *first*, and the multiplier is
applied to that already-reduced value (never below zero). This is deliberately
*not* `base_value x multiplier - hazard_count`. The relic's `sigil` is carried
across unchanged. If a chamber holds **no** relic, its `relic_worth` is `0` and
its sigil is the placeholder `-`.

**Rule II.3 (selection among candidates).** The season-archive is a *mixed* dump,
so a single room may list **more than one** candidate guardian (several monster
rows sharing its `room_id`) and **more than one** candidate relic. The chamber
takes exactly one of each:

* the guardian is the candidate with the **highest `base_hp`**; ties are broken by
  the **lowest `monster_id`**.
* the relic is the candidate with the **highest `base_value`**; ties are broken by
  the **lowest `relic_id`**.

The candidates that were examined but *not* chosen are **superseded** -- they
contribute nothing to the chamber, but they were still consulted (Appendix V).
Monster/relic rows whose `room_id` matches **no** room are **orphans**: they belong
to no chamber and are never consulted.

All of these quantities are whole numbers; no rounding is ever required.


# Appendix III -- The Binder's Format (`vault.pack`)

The migrated database is a single little-endian binary image written to
`/app/out/vault.pack`. The binder's format is fixed:

```
Header (8 bytes):
    magic          : 4 bytes  = the ASCII letters  R V P 1
    chamber_count  : uint32   (little-endian)

Chamber record (53 bytes each, one per chamber, in chamber_index order):
    room_id        : uint16   (little-endian, unsigned)
    chamber_index  : uint16   (little-endian, unsigned)
    guard_hp       : int16    (little-endian, signed)
    guard_atk      : int16    (little-endian, signed)
    relic_worth    : int16    (little-endian, signed)
    hazard_count   : uint8
    biome_code     : uint8    (crypt=0, forge=1, mire=2, vault=3)
    sigil          : 1 byte   (one ASCII character, 'A'..'F' or '-')
    name           : 24 bytes (ASCII room name, NUL-padded, truncated to 24)
    species        : 16 bytes (ASCII guardian species, NUL-padded, truncated to 16)

Footer (4 bytes):
    magic          : 4 bytes  = the ASCII letters  R V P E
```

The chamber records appear in ascending `chamber_index` order. The struct format
string `"<HHhhhBBc24s16s"` packs one record exactly.


# Appendix IV -- The Expedition Rites (the replay engine)

The terminal engine replays a scripted expedition over the migrated `vault.pack`
and writes a transcript to `/app/out/transcript.txt`. The script is read one
action per line; blank lines and lines beginning with `#` are skipped and do not
advance the turn counter. The four actions are `ADVANCE`, `STRIKE`, `GRAB`,
`BRACE`.

**The delver begins** with `hp = 25`, `atk = 4`, `score = 0`, and standing
*before* the first chamber at position `-1`. Health never exceeds the cap of 25.
Each chamber's guardian starts at its full `guard_hp`; a guardian at or below 0
hit points is *slain*.

**ADVANCE** -- step to the next chamber (`pos += 1`). On arrival the event is
`enter <chamber name>`. If the delver is already at the last chamber, the position
does not change and the event is `EDGE`.

**STRIKE** -- attack the guardian of the current chamber.
* If there is no current chamber, or its guardian is already slain, the event is
  `EMPTY` and nothing changes.
* Otherwise the guardian loses `atk` hit points. If it is **still alive** (hit
  points remain above 0) it retaliates for its `guard_atk`: the delver loses that
  much health. A *survived* retaliation also costs the delver their battle
  momentum -- immediately after the trade the delver's `atk` drops by 1, but
  never below the starting value of 4 -- and the event is `TRADE -<guard_atk>`.
  If that blow instead drops the delver to 0 or below, health is pinned at 0, the
  event is `DOWNED -<guard_atk>`, and the expedition ends immediately (no further
  lines are processed; `atk` is left unchanged on a downing blow).
* If instead the strike **slays** the guardian (hit points fall to 0 or below),
  the guardian does *not* retaliate, the delver's `atk` rises by 1 (battle-honed),
  and the event is `SLAIN`. (So `atk` ratchets up by 1 for every guardian slain
  and back down by 1 for every wound survived, floored at the starting 4.)
  Slaying also extends the delver's **kill streak** and pays a *slayer's tithe* to
  the score. The engine keeps a streak counter that begins at `0`; each `SLAIN`
  raises it by 1 and adds the **new** streak value to `score` -- so consecutive
  kills pay `+1`, then `+2`, then `+3`, and so on. The streak **resets to 0** after
  *any* action whose event is not `SLAIN` (a `TRADE`, `EMPTY`, `ADVANCE`, `GRAB`,
  `BRACE`, `WARDED`, ... all break the chain; only back-to-back `SLAIN`s build it).

**GRAB** -- claim the current chamber's relic. The claim succeeds only if the
chamber's guardian is slain, the chamber holds a relic (`relic_worth > 0`), and the
relic has not already been taken: `score += relic_worth`, the relic is marked
taken, and the event is `CLAIM +<relic_worth>`. In every other case the event is
`WARDED` and nothing changes.

**BRACE** -- recover `min(25, hp + 3) - hp` health (3, unless near the cap). The
event is `BRACE +<amount actually restored>`.

**Transcript lines.** After every action the engine appends exactly one line:

```
<turn> <action> pos=<pos> hp=<hp> atk=<atk> score=<score> | <event>
```

formatted with these field widths (C `printf` / Python format spec):

* `turn`   -- `%03d` (1-based, increments once per non-comment action)
* `action` -- `%-7s` (left-justified in a 7-wide field)
* `pos`    -- `pos=%+03d` (signed, zero-padded to two digits after the sign)
* `hp`     -- `hp=%03d`
* `atk`    -- `atk=%02d`
* `score`  -- `score=%05d`
* then a literal ` | ` and the event text.

**The final line** is the summary, with no leading turn number:

```
RESULT status=<ALIVE|DOWNED> hp=%03d atk=%02d score=%05d cleared=%02d turns=%03d
```

where `status` is `DOWNED` if the delver fell and `ALIVE` otherwise; `cleared` is
the number of chambers the delver reached (index `0..max_pos`) whose guardian is
slain (a chamber with no guardian counts as cleared once reached); and `turns` is
the number of action lines processed. The transcript ends with a single trailing
newline.


# Appendix V -- The Binder's Consulted Ledger (`consulted.json`)

A migration that only writes the chosen chambers leaves no trail of what it
*looked at*. The binder is held to a higher standard: alongside `vault.pack`, the
`pack` migration writes an audit of its **consulted scope** to
`/app/out/consulted.json`.

The consulted scope is **every guardian-candidate and relic-candidate the
migration examined while deriving chambers** -- not the ones it *selected*. A
candidate is *examined* if and only if its `room_id` is the room of some chamber.
This therefore includes:

* the selected guardian/relic of every chamber, **and**
* every **superseded** candidate (Rule II.3) for those same rooms -- candidates the
  binder weighed and set aside.

It **excludes orphans**: a monster or relic whose `room_id` is not a chamber's room
was never examined and must **not** appear. (The chosen-only set and the
everything-including-orphans set are both wrong; only the *examined* set is right.)

The file is a JSON object with exactly two keys, each an array of integer ids
sorted **ascending**:

```
{
  "guardians_consulted": [ <monster_id of every examined guardian-candidate> ],
  "relics_consulted":    [ <relic_id   of every examined relic-candidate>   ]
}
```

It is serialised with `json.dumps(manifest, sort_keys=True, indent=2)` followed by a
single trailing newline, exactly like the schema report of Appendix I.
