Several issues in /app affect refund processing and per-student booking limits.

When a student cancels a booking with active cancellation coverage, they receive a refund. The function that determines whether a booking qualifies for a refund is not correctly checking the cancellation coverage flag — it always reports a booking as eligible regardless of whether coverage was purchased. When only some wheels in a booking are cancelled, the refund is prorated based on how many wheels are being returned. The proration calculation is not producing the correct value.

The platform limits each student to 8 wheels per class session, counted cumulatively across all their reservations for that session. The current tracking code replaces the stored count on each new booking instead of adding to it — so a student who books 5 wheels in one reservation and 4 more in a second reservation accumulates only 4 wheels on record rather than 9, well under the limit. Both bookings succeed, and any subsequent booking is also allowed because the true running total is never stored. The limit check must also be inclusive: a student who has already accumulated exactly 8 wheels must not be allowed any additional wheels. The fix belongs in /app/student.py, not in reservation_system.py.
