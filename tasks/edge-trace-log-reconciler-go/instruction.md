The edge telemetry team has a JSONL export from several log shippers, and the replay report they use for billing disputes is wrong when retries, voids, and service capacity overlap. Build a Go CLI that replays the log deterministically and writes the reconciled report.

Create `/workspace/log_reconciler.go`. It must run as:

`go run /workspace/log_reconciler.go /workspace/task_file/config.json /workspace/task_file/events.jsonl /workspace/out/report.json`

The first argument is a JSON config object with `routes` as an object from service name to an array of allowed next services, `capacities` as an object from service name to positive integer capacity, `trusted_nodes` as an array of node names, `void_grace_ms` as a non-negative integer, `trace_byte_cap` as a non-negative integer, and `billable_statuses` as an array of integer HTTP statuses. The second argument is JSON Lines. Each line is one event object with these fields: `event_id` string, `ts` RFC3339 timestamp ending in `Z`, `node` string, `seq` integer, `trace` string, `kind` lowercase string, `service` string or null, `next_service` string or null, `bytes` integer or null, `status` integer or null, `target` string or null, `flags` array of lowercase strings, and `req` string or null. The output path's parent directory may not exist yet.

Replay all input records in canonical order, not file order: ascending `ts`, then ascending `node`, then ascending `seq`, then ascending 1-based input line number. A duplicate log-shipping position is any later record with the same `node` and `seq` as an earlier canonical record. Duplicate-position records are `ignored` with reason `duplicate_position`, do not mutate state, and still appear in the audit in canonical order.

Valid `kind` values are `start`, `hop`, `bytes`, `end`, and `void`. Missing fields, wrong JSON types, bad timestamps, unknown kinds, negative `bytes`, and unknown services are rejected with additive reasons in this exact order when applicable: `invalid_schema`, `unknown_kind`, `unknown_service`, `trace_not_active`, `trace_already_active`, `service_mismatch`, `route_not_allowed`, `capacity_full`, `loop_blocked`, `target_missing`, `target_not_voidable`, `target_trace_mismatch`, `target_already_voided`, `void_too_late`. Rejected records do not mutate state and appear in the audit. Reasons are additive, not short-circuiting, except a schema-invalid record only needs `invalid_schema`.

A `start` requires `service` and `req`, opens a trace only when that trace is not active, the service is known, and the service has free capacity. It sets the request path to `[service]`, status to `open`, raw bytes to 0, and increments that service's active count. A `hop` requires an active trace, `service` equal to the trace's current service, `next_service` known, the route `service -> next_service` allowed by config, destination capacity free, and `next_service` not already in that trace's path unless `loop_ok` is in `flags`; on acceptance it moves active capacity from `service` to `next_service` and appends `next_service` to the path. A `bytes` event requires an active trace and matching `service`; on acceptance it adds billable raw bytes for that trace. If `sampled` is in `flags`, the accepted contribution is floor(`bytes` / 2), and the request warning `sampled_bytes` must appear once. An `end` requires an active trace, matching `service`, and integer `status`; on acceptance it closes the trace, records `closed_at` and `status_code`, and releases service capacity. A `void` never changes active trace or capacity state. It requires `target` to name an accepted `bytes` event, the same `trace` as the target, a target not already voided, and a timestamp no more than `void_grace_ms` after the target timestamp. On acceptance it subtracts that accepted bytes contribution and writes a void adjustment.

Capacity checks use the active counts at the moment each event is replayed. `capacity_full` is emitted for a start or hop only when every other precondition needed to identify the destination service is valid and that destination is already at capacity. For `hop`, source capacity is released and destination capacity is acquired in the same accepted transition; a hop from a service to itself is allowed only if the route exists and `loop_ok` is present. When an accepted hop uses `loop_ok`, the request warning `loop_allowed` must appear once. Warnings are sorted lexicographically.

The report must be exact JSON after parsing, with these top-level fields: `requests`, `audit`, `adjustments`, `peaks`, and `summary`. Sort `requests` by `trace`; include one request for every accepted `start`, including open traces. Each request object has `trace`, `req`, `opened_at`, `closed_at` as string or null, `status` as `open` or `closed`, `status_code` as integer or null, `final_service`, `path`, `raw_bytes`, `billable_bytes`, and `warnings`. `raw_bytes` is accepted bytes after voids. `billable_bytes` is 0 for open traces and for closed traces whose `status_code` is not in `billable_statuses`; otherwise it is `min(raw_bytes, trace_byte_cap)`.

Sort `audit` in canonical event order. Each audit object has `event_id`, `line`, `action` as `accepted`, `rejected`, or `ignored`, and `reasons` as an array. Sort `adjustments` by `trace`, then `kind`, then `source_event`, then `event_id`. A void adjustment has `kind: "void"`, `amount` equal to the negative accepted contribution of the target bytes event, `event_id` from the void event, and `source_event` from the target event. After replay, also add one final adjustment for each request whose raw bytes differ from billable bytes: `kind` is `cap` when the closed billable request exceeded `trace_byte_cap`, otherwise `nonbillable`; `amount` is `billable_bytes - raw_bytes`; `event_id` is the accepted end event id for closed traces or null for open traces; `source_event` is the accepted start event id. Sort `peaks` by service name; each object has `service` and `peak`, the maximum active count observed after each accepted `start`, `hop`, or `end`. The `summary` object has integer fields `processed`, `accepted`, `rejected`, `ignored`, `open_requests`, `closed_requests`, and `billable_total`.
