Our batch reconciler for smart-meter exports is producing wrong TOU splits, demand peaks, gap counts, and reconciliation flags. Fix the C sources under `/app/environment` so the normal build and run path emits a correct report for every fixture listed by the run config.

Rebuild with `make -C /app/environment`, then run:

`/app/bin/tou_reconcile --config /app/environment/config/run.json --out /app/output/reconciliation_report.json`

Do not hand-edit `/app/output/reconciliation_report.json`; the verifier rebuilds, reruns, and checks the generated JSON.

Tariff parameters, seasons, and TOU window tables live in the tariff JSON named by each run config, so do not hardcode the bundled `/app/environment/config/tariffs.json` values. Each fixture CSV has `meter_id,timestamp,register_kwh` columns and may use normal CSV quoting for commas or quotes inside a meter id. Rows may be interleaved across meters and are not guaranteed to be sorted; process each meter by absolute timestamp order. Timestamps are ISO-8601 with numeric offsets and may include fractional seconds. The first chronological row of each meter is a baseline register reading only; do not assign tiers or demand from it. Preserve fixture names and meter ids exactly in the JSON, even when ids are long or contain JSON-special characters, and include every fixture and every distinct meter from the active config instead of relying on the old fixed-size limits. Some CSVs add a fourth `quality` column: blank or `actual` rows are normal, `estimate` rows contribute energy but make that meter unreconciled, `void` rows are ignored, and `reset` rows become a new baseline without creating an interval across the reset. If the same meter has multiple non-reset valid rows at the exact same absolute timestamp, treat them as correction rows: keep only the last one in CSV order as the reading for that timestamp. When an `actual` or `estimate` row at a timestamp is followed by a duplicate `reset` row at that same timestamp, the actual/estimate reading still closes the previous interval, and the reset reading then becomes the baseline for following intervals; do not count that duplicate reset as a rollover.

A meter reconciles when its summed interval energy and `register_delta_kwh` agree within 0.001 kWh, and `all_reconciled` is true only when all meters reconcile. Tier output keys are `off_peak`, `mid_peak`, and `on_peak`. The top-level `timezone` string must match the active tariff config label.

Output schema at `/app/output/reconciliation_report.json`:

- top-level `timezone` (string), `all_reconciled` (bool), `fixture_sets` (array)
- each fixture set object: `name` (string), `meters` (object keyed by meter id)
- each meter: `interval_count` (int, interval rows used), `total_kwh` (number), `tier_kwh` (object with the three tier keys), `demand_peak_kw` (number), `rollover_events` (int), `gap_intervals` (int), `reconciled` (bool), `register_delta_kwh` (number)

See `/app/environment/docs/schema.md` for field names. Apply TOU tiers from configured slot start timestamps using each slot's written local date and clock; tariff windows include their start minute and exclude their end minute, including wrapped overnight windows. Summer uses the inclusive `start_mmdd` and `end_mmdd` values from the tariff JSON, with all other dates treated as winter. When two consecutive valid readings are more than one configured interval apart, spread that register delta evenly across each elapsed configured slot before adding tier kWh or demand; `gap_intervals` is the number of missing slots. If a generated slot crosses a season or TOU-window boundary, split that slot's kWh by exact overlap seconds before adding to `tier_kwh`; do not classify the entire slot only by its first minute. `demand_peak_kw` is the maximum prorated slot kW sample (`slot_kwh * 60 / interval_minutes`), not an average. Gap and slot counts are based on full elapsed absolute time between consecutive readings, so calendar boundaries, fractional seconds, and offset changes still count correctly. If a register rolls over, use the full wrap delta: `(register_max_kwh - previous_register) + current_register`.
