The accounting team runs a nightly batch job that produces `/app/transactions.tsv`, a tab-delimited log of bank account activity. Write a Wren script at `/app/audit.wren` that reads this file and generates a JSON audit report at `/app/audit_report.json`. Run it with `wren_cli /app/audit.wren`.

Each row holds six tab-separated fields: `txn_id`, `account_id`, `date`, `amount`, `type`, and `currency`. Any row missing one of these fields should be flagged as `MISSING_FIELD` and skipped; every other check applies only to complete rows. A complete row can trigger more than one format error: transaction IDs must be a `T` followed by exactly nine digits (`BAD_TXN_ID`); account IDs must be `AC` followed by exactly six digits (`BAD_ACCT_ID`); dates must be valid calendar dates in `YYYYMMDD` format no later than 2026-06-13 (`BAD_DATE`); amounts must be non-negative decimals (`BAD_AMOUNT`); the type must be one of `CREDIT`, `DEBIT`, `FEE`, `INTEREST`, or `REVERSAL` (`BAD_TYPE`); and the currency must be one of `USD`, `EUR`, `GBP`, `JPY`, or `CHF` (`BAD_CURRENCY`).

Two checks apply to every complete row regardless of its format validity: a transaction ID that has already appeared is flagged `DUPLICATE_TXN` on the second and any later occurrence, and a `FEE` whose amount exceeds 25.00 is flagged `FEE_OVERCAP`.

The remaining rules are per-account and operate only on each account's *valid records* — the complete rows that passed all six format checks and are the first occurrence of their transaction id. Within an account, if more than five `DEBIT` valid records fall on the same calendar date, every one of those debits is flagged `HIGH_VELOCITY` and is placed on hold: a held debit does not affect the running balance and cannot be cancelled by a reversal, so a high-velocity debit is never also flagged for an overdraft.

Process each account's remaining valid records (everything except its held debits) in chronological order, by date and then by `txn_id`, with a running balance that starts at zero. `CREDIT` and `INTEREST` increase the balance; `DEBIT` and `FEE` decrease it and become open charges. A `REVERSAL` cancels one of the account's still-open charges that has the same amount and has not already been cancelled, adding that amount back to the balance; each charge can be cancelled at most once, and a `REVERSAL` that matches no such charge is flagged `UNMATCHED_REVERSAL` and leaves the balance unchanged. Any `DEBIT` or `FEE` that drives the running balance below zero is flagged `OVERDRAFT`.

The output must be a JSON array whose elements each have four string fields: `txn_id`, `account_id`, `error_code`, and `detail` (a short human-readable description of the violation). Sort the array by `account_id` ascending, then by `error_code` ascending within an account, and finally by `txn_id` ascending to break further ties.
