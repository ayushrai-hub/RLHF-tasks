Cookie auditor contract. The CLI runs as `/tmp/cookie-auditor --policy <policy.json> --events <events.jsonl> --output <report.json>` and writes the report JSON to the requested output path. The sample inputs in `/app/task_file/input/` are read-only fixtures.

`policy.json` contains `public_suffixes`, `sensitive_name_patterns`, and `max_cookie_header_bytes`. `events.jsonl` is ordered; response events have `id`, `url`, and `set_cookie`, while request events have `id`, `url`, `method`, `top_level_site`, and `is_top_level_navigation`. Process events strictly in input order. Response events may mutate the jar; request events are read-only.

For each Set-Cookie header, split the first semicolon-separated part on the first `=` only. Trim surrounding whitespace from the cookie name and value. Values may contain more `=` characters, and an empty value is valid when the trimmed name is nonempty. Ignore blank attribute segments. Attribute names are case-insensitive, and if the same attribute appears multiple times in one header, the later value wins. Missing SameSite is `Lax`; invalid SameSite values also behave as `Lax`. A header whose first semicolon-separated part has no `=`, such as `noval`, is malformed: treat it as a cookie with name `""`, reject it with reason `empty_name`, and emit the rejection record with `"name": ""`. A blank header follows the same rule. Empty-name cookies are never accepted.

The default cookie path is the URL path up to but excluding the rightmost `/`, or `/` when there is no parent path. So `https://app.example/a/b/login` defaults to `/a/b`, `/login` to `/`, `/` to `/`, and `https://app.example.com` to `/`.

Apply Set-Cookie rejection reasons in this exact priority when multiple could apply: `empty_name`, `public_suffix_domain`, `domain_not_suffix`, `samesite_none_without_secure`, `secure_prefix_without_secure`, `host_prefix_invalid`. A Domain attribute that is itself one of the configured public suffixes is `public_suffix_domain` before any suffix-of-origin check. Domain attributes should be lowercased and stripped of one or more leading dots for storage and matching. If that normalization leaves an empty domain string, reject the header with `domain_not_suffix`. URL ports do not participate in host/domain matching.

`Max-Age` values are integers. If `Max-Age <= 0`, it is a deletion directive and removes a stored cookie only when name, domain, and path all match exactly. Increment `deleted` and emit a deleted cookie key only for an actual removal. Never increment `accepted` for a deletion directive, even if it does not match anything. If `Max-Age` is present but not a valid integer, treat it like an ordinary attribute and accept the cookie if all other checks pass.

Host-only cookies match only the exact request host. Domain cookies match that domain and its subdomains. Same-site comparison uses the request host's registrable site against lowercase `top_level_site`; when multiple configured public suffixes match, use the longest suffix before taking the preceding label. SameSite `Strict` requires same site. SameSite `Lax` allows same site or a top-level GET navigation, and request methods are compared case-insensitively. SameSite `None` requires Secure.

Prefix checks are byte/string case-sensitive. Only names beginning exactly with `__Secure-` trigger `secure_prefix_without_secure`, and only names beginning exactly with `__Host-` trigger `host_prefix_invalid`. Near misses such as `__secure-lower`, `__SECURE-upper`, `__host-lower`, or `__HOST-upper` are ordinary names for prefix-rule purposes.

For every response event, emit one response report in input order and do not emit response reports for request events. Each response report has `id`, `accepted_cookie_keys`, and `deleted_cookie_keys`. Accepted keys are `{name,domain,path}` for accepted stored cookies from that response in Set-Cookie header order after normalization. Deleted keys are `{name,domain,path}` only for deletion directives that actually removed an existing cookie. Rejected headers and non-matching deletions do not appear in either array.

When an accepted Set-Cookie has the same `(name, domain, path)` as an existing cookie, remove the old cookie and append the new one at the end of the jar. This current jar order is the creation order used for sending and blocking. Build request Cookie headers by scanning the current jar once in order. Eligible sent pairs are `name=value` joined by `; `. Use UTF-8 byte length of the exact fragments and separators for `max_cookie_header_bytes`; never count runes. If an eligible cookie would exceed the limit, block only that cookie with `header_limit`, continue scanning later cookies, and send a later eligible cookie if it fits. If the limit is zero, every eligible cookie is blocked with `header_limit`, `cookie_header` is `""`, and `header_bytes` is `0`.

Cookie blocking reasons are `domain_mismatch`, `path_mismatch`, `secure_only`, `samesite_strict`, `samesite_lax`, and `header_limit`. Append `sent_cookies`, `sent_cookie_keys`, `blocked_cookies`, and `blocked_cookie_keys` in the same jar scan order. `sent_cookies` contains sent names only. `sent_cookie_keys` contains `{name,domain,path}`. `blocked_cookies` contains `{name,reason}`. `blocked_cookie_keys` contains `{name,domain,path,reason}`. `cookie_header` is the exact wire header string or `""`; `header_bytes` is its UTF-8 byte length. Include blocked entries for all blocked cookies; do not coalesce by name, domain, or path.

The output JSON must be exactly `{summary,responses,set_cookie_audit,requests,rejections,domain_diagnostics,request_diagnostics,cookie_lifecycle,jar_snapshots,stored_cookies}`. Response rows have exactly `id,accepted_cookie_keys,deleted_cookie_keys`. Request rows have exactly `id,sent_cookies,sent_cookie_keys,blocked_cookies,blocked_cookie_keys,cookie_header,header_bytes`. Rejections have exactly `event_id,name,reason`. Stored cookies have exactly `name,domain,path,host_only,secure,http_only,same_site,risks` and must be emitted in final jar order.

Risks are `overbroad_domain`, `missing_secure`, and `missing_httponly`, emitted in that order when present. `overbroad_domain` applies to every stored domain cookie. `missing_secure` applies to every stored cookie without Secure. `missing_httponly` applies only to stored cookies whose name matches at least one `sensitive_name_patterns` regular expression and that lack HttpOnly. Match sensitive-name patterns case-insensitively against the cookie name. `summary` has exactly `accepted,set_cookie_rejected,deleted,request_count,risk_counts,truncated_requests`; `risk_counts` counts final stored-cookie risks, sorts keys lexicographically, and omits zero-count risk names.

The audit sections below are views of the same event processing state used for `responses`, `requests`, and `stored_cookies`; do not run a separate parser or alternate matching model for them. A normalized field in an audit row must use the same final duplicate-attribute value, default path, SameSite fallback, domain normalization, cookie identity, and jar order that controlled the actual accept, reject, delete, send, or block decision. Audit rows do not themselves mutate the jar or counters beyond the behavior already described above.

`domain_diagnostics` is sorted lexicographically by domain. Include every domain that appears in the final stored jar or had at least one cookie sent or blocked during any request, even if it has zero stored cookies by the end. Each row has exactly `domain,stored_cookie_count,host_only_cookie_count,secure_cookie_count,sent_count,blocked_count,risk_counts`. Stored, host-only, secure, and risk counts are computed from the final jar for that domain. Sent and blocked counts increment once per sent or blocked cookie on each request, including `header_limit`. Per-domain `risk_counts` follows the same risk rules as summary and is `{}` when the domain has no stored-cookie risks.

`set_cookie_audit` contains one row for every Set-Cookie header in response-event order, including rejected headers and deletion directives that do not remove anything. Each row has exactly `event_id,index,name,domain,path,host_only,secure,http_only,same_site,max_age_state,disposition,reason`. `index` is the zero-based index of that header within its response event. `name` is the trimmed parsed cookie name, or `""` for malformed or blank headers. For `empty_name` rows, use `domain: ""`, `path: ""`, `host_only: false`, `secure: false`, `http_only: false`, `same_site: "Lax"`, `max_age_state: "absent"`, `disposition: "rejected"`, and `reason: "empty_name"`. For parsed-name rows, `domain`, `path`, `host_only`, `secure`, `http_only`, and `same_site` are the normalized values after duplicate attributes have been resolved by the later-value-wins rule and after default path and SameSite fallback are applied. `max_age_state` is `"absent"` when no Max-Age attribute remains after duplicate resolution, `"invalid"` when the final Max-Age value is not an integer, `"delete"` when the final integer is `<= 0`, and `"positive"` when it is `> 0`. `disposition` is one of `"accepted"`, `"deleted"`, `"ignored_delete"`, or `"rejected"`. Use `"deleted"` only for a deletion directive that actually removed an existing exact `(name,domain,path)` identity; use `"ignored_delete"` for non-matching deletion directives. `reason` is the rejection reason for rejected rows and `""` otherwise.

`request_diagnostics` contains one row per request event in input order. Each row has exactly `id,registrable_site,top_level_site,same_site_context,eligible_cookie_keys,sent_cookie_keys,blocked_reason_counts,header_limit_bytes_skipped`. `registrable_site` is the request host's registrable site using the same longest-public-suffix rule as SameSite. `top_level_site` is the lowercased event `top_level_site`. `same_site_context` is true only when those two strings are equal. `eligible_cookie_keys` lists `{name,domain,path}` for cookies that pass domain, path, Secure, and SameSite checks before applying `max_cookie_header_bytes`, in jar scan order; cookies later blocked by `header_limit` are still eligible and must appear here. `sent_cookie_keys` repeats the request row's sent keys. `blocked_reason_counts` counts every blocked cookie on that request by final blocking reason, omits zero-count reasons, and sorts keys lexicographically. `header_limit_bytes_skipped` is the sum of UTF-8 byte lengths of the `name=value` fragments for eligible cookies blocked specifically by `header_limit`, excluding `; ` separators.

`cookie_lifecycle` contains one row for every `(name,domain,path)` identity that was ever accepted into the jar, sent, blocked, or actually deleted. Non-matching deletion directives and rejected Set-Cookie headers do not create lifecycle rows. Rows are sorted by `domain`, then `path`, then `name`, all lexicographically. Each row has exactly `name,domain,path,accepted_count,replaced_count,deleted_count,sent_count,blocked_count,first_event_id,last_event_id,final_state`. `accepted_count` increments for each accepted Set-Cookie for that exact identity, including accepted replacements. `replaced_count` increments when an accepted Set-Cookie removes an existing cookie with the same exact identity before appending the new one. `deleted_count` increments only for an actual deletion directive removal. `sent_count` and `blocked_count` increment once per request where that identity is sent or blocked. `first_event_id` and `last_event_id` are the IDs of the first and last events that changed or observed that identity through one of those accepted, replaced, deleted, sent, or blocked actions. `final_state` is `"stored"` if that exact identity remains in the final jar, otherwise `"absent"`.

`jar_snapshots` contains one row after every response event, in response event input order, after all Set-Cookie headers in that response have been processed. Do not emit jar snapshots for request events. Each row has exactly `id,stored_count,host_only_count,domain_cookie_count,secure_count,jar_cookie_keys,risk_counts`. `id` is the response event ID. The count fields and `risk_counts` are computed from the jar state at that moment, using the same risk rules as final `stored_cookies`. `jar_cookie_keys` lists `{name,domain,path}` for every stored cookie in current jar order at that moment, after any replacements have moved an identity to the end and after actual deletions have removed identities. `risk_counts` sorts keys lexicographically and omits zero-count risk names.

All arrays in the schema must serialize as arrays even when empty: `responses`, `set_cookie_audit`, `requests`, `rejections`, `domain_diagnostics`, `request_diagnostics`, `cookie_lifecycle`, `jar_snapshots`, `stored_cookies`, `accepted_cookie_keys`, `deleted_cookie_keys`, `sent_cookies`, `sent_cookie_keys`, `blocked_cookies`, `blocked_cookie_keys`, `eligible_cookie_keys`, `jar_cookie_keys`, and `risks`. All objects in the schema must serialize as objects even when empty, including `summary`, every `risk_counts`, and every `blocked_reason_counts`.
