Now wire the parser into actual persisted job state. We need jobs to survive restarts, fire on schedule from a background loop, expose a REST surface for create / get / list-executions / pause / resume / trigger-now, and apply the right misfire instruction when the scheduler wakes up and discovers it slept past a fire time.

The H2 schema in `/app/src/main/resources/schema.sql` is already created at boot and gives you `cron_jobs` and `cron_executions`. The job lifecycle: on create, compute the next fire time from the cron expression and store it on the row. The scheduler loop wakes once per second, scans `cron_jobs` for `state='ACTIVE' AND next_fire_time <= now`, inserts a `PENDING` row into `cron_executions` per due job, advances `next_fire_time` to the next cron time after the one it just fired, and signals the dispatcher. The dispatcher (still single-threaded at this milestone — concurrency lives in milestone 3) pulls one PENDING row at a time, looks up the `JobBean` by class name through `JobRegistry`, runs it, marks the row `SUCCEEDED` with the bean's returned String written into the `error_message` column (yes, the column name's bad — treat it as the outcome message; `LoggingJob` returns a `logged-at:<instant>` marker, `SlowJob` returns `slow-done:<id>`), or `FAILED` with the exception's short description there instead. The three built-in beans `LoggingJob` / `SlowJob` / `FailingJob` are already on the classpath. `trigger-now` inserts a PENDING row at `now` regardless of the cron schedule.

Misfire policy is per-job. `FIRE_NOW` runs the missed fire immediately at the current instant and resumes the cron schedule from now. `DO_NOTHING` silently drops the missed fires and recomputes the next fire time from now. `FIRE_NEXT_WITH_REMAINING_COUNT` writes one summary execution row with status `MISFIRED` (no body invocation) and resumes from now. A fire is considered misfired when it's more than `chronos.misfire.thresholdSeconds` (60) behind the clock. The verifier hits `POST /api/_test/advance-clock?seconds=N` to push the injected `Clock` forward and observe how each policy responds; both the scheduler loop's tick and `POST /api/jobs/{id}/resume` after a pause have to consult the misfire handler.

REST responses follow the DTOs already declared under `/app/src/main/java/com/snorkel/chronos/dto/`. A `JobResponse` is `{id, name, jobClass, cronExpr, zone, misfire, concurrentExecutionDisallowed, state, nextFireTime, createdAt, executions}` — `executions` populated on `GET /api/jobs/{id}` and empty on `POST /api/jobs`. An `ExecutionResponse` is `{id, jobId, scheduledTime, status, startedAt, completedAt, errorMessage, lastHeartbeat, workerId, recoveryAttempt}` with timestamps as ISO instants. `GET /api/jobs/{id}` on an unknown id returns 404 with a body that includes the string `job_not_found`; bad cron / unknown job class / mutually-? violations on `POST /api/jobs` return 400. `GET /api/jobs/{id}/executions?limit=N` returns the most recent N rows for that job. The DAO methods in `/app/src/main/java/com/snorkel/chronos/repository/` and the scheduler / dispatcher / misfire-handler skeletons in `/app/src/main/java/com/snorkel/chronos/scheduler/` are the surface to fill in; the controller signatures are wired but the bodies throw. Rebuild with `mvn -B -DskipTests package` before the verifier runs.
