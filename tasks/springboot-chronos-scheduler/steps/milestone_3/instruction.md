The single-threaded dispatcher needs to grow up. Now we need a worker pool of `chronos.workers` threads (default 4) that pull PENDING executions concurrently, claim each row atomically so no two workers ever run the same execution, write per-second heartbeats while the job is in flight, and recover automatically when a worker crashes mid-run without finalising the row.

The atomic-claim contract is non-negotiable. We've seen production schedulers ship with `SELECT WHERE status='PENDING' LIMIT 1` followed by a separate `UPDATE SET status='CLAIMED'` and end up firing the same job ten times because two workers won the same race. The claim has to be one round-trip — `SELECT ... FOR UPDATE` followed by an `UPDATE ... WHERE id=? AND status='PENDING'` returning rowcount, or any other H2 idiom that gives you single-writer semantics; what matters is that under 20 concurrent `trigger-now` POSTs against a job, exactly 20 execution rows exist and each one was claimed by exactly one worker. Add the `concurrent_execution_disallowed` flag while you're in there — when it's set on the job and the dispatcher tries to claim a new execution whose `job_id` already has a `CLAIMED` or `RUNNING` sibling, the new row gets marked `SKIPPED` with the literal string `concurrent_execution_disallowed` in `error_message` (the `errorMessage` field on `ExecutionResponse`) instead of running.

Heartbeats and failover are the other half. While a `JobBean` is executing, the `HeartbeatRegistrar` background thread writes `last_heartbeat = now` on its row roughly once per second; `RunningJobsRegistry` already tracks the worker thread, so `untrack`-ing on completion or crash is what stops the heartbeats. A second background loop, the `FailoverDetector`, runs every 5s and looks for `CLAIMED` or `RUNNING` rows whose `last_heartbeat` is older than `chronos.heartbeat.timeoutMs` (10s). Each one gets marked `FAILED` with the literal string `worker_lost_heartbeat` in `error_message`, and a fresh `PENDING` row is inserted at the same `scheduled_time` with `recovery_attempt = previous + 1`, up to `chronos.heartbeat.maxRecoveryAttempts` (3) — past that, no new row, the execution stays FAILED. The verifier drives this with `POST /api/_test/simulate-crash/{execution_id}` which interrupts the worker thread without finalising the row. The skeletons and `@Component` wiring for `JobDispatcher`, `HeartbeatRegistrar`, `FailoverDetector`, `ExecutionDao` already exist under `/app/src/main/java/com/snorkel/chronos/` — fill in the bodies. Rebuild with `mvn -B -DskipTests package` before the verifier runs.
