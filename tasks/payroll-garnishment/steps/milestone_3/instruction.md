Add a remittance run, a persisted remittance journal, and a tamper-evident audit chain; all earlier commands keep working. Integer cents only.

`remit <employee>` computes one gross-up figure per order and records it as an audit run. For each of the employee's orders in allocation order, ascending priority then ascending id, treat the order's cap as a target net and compute the milestone-two gross-up of that cap, the smallest whole-cent gross whose forward net is at least the cap. It prints "<order_id> <kind> <amount>" per order in that same allocation order, where amount is that order's gross-up figure, and additionally appends one audit entry per printed line in that same order. Running remit again for the same employee appends a fresh set of audit entries after the existing ones (the journal is append-only). An employee with no orders prints nothing and exits zero. Print not_found (exit non-zero) for an unknown employee.

Each audit entry captures a 1-based seq, the employee id, the order id, the order kind, and the gross-up amount. The entry's canonical message is the exact ASCII "<seq>|<employee_id>|<order_id>|<kind>|<amount>|<prev_hash>" with no spaces and no trailing delimiter, prev_hash being 64 zero characters for seq 1 else the prior entry hash. The entry hash is the lowercase-hex HMAC-SHA256 of that message keyed by PAY_AUDIT_SECRET (default pay-audit-key). `audit` prints "<seq> <employee_id> <order_id> <kind> <amount> <entry_hash>" per audit entry in sequence order.

`audit-verify` recomputes the chain and prints valid, else broken_at <seq> <reason> for the first failure, the reason being seq_gap when the sequence is not contiguous from 1, then prev_hash_mismatch, then entry_hash_mismatch, in that precedence; it always exits zero. As before every reported word and figure, including valid, the broken_at lines, and the not_found word, goes to standard output. With `--chain <base64-json>` verify that supplied chain instead under the same rules: the argument is standard padded base64 of a UTF-8 JSON array of entries in order, each carrying exactly seq, employee_id, order_id, kind, amount, prev_hash, and entry_hash. Walk from the 64-zero genesis with a running previous hash; at 0-based index i (expected seq i+1) report broken_at <i+1> seq_gap when seq is not i+1, else broken_at <seq> prev_hash_mismatch when prev_hash differs from the running previous, else recompute the HMAC over this entry's own fields and report broken_at <seq> entry_hash_mismatch when it differs; on a pass advance the running previous to this entry's hash.
