# Transfer Rules

The scenario JSON has an origin body, an epoch, requested targets, and a list of arcs. Each arc connects `from` to `to` and provides launch timing and cost information through `depart`, `duration`, `dv`, and `dose`. A positive `period` repeats that launch window; use the first repeated departure that is not earlier than the plan's current arrival time.

Arcs may grant, require, consume, or forbid named resource tokens. A path may use an arc with `requires` only after earlier arcs in that same path have granted every required token. A path may use an arc with `consumes` only when those tokens are currently available; consumed tokens are removed before the arc's `grants` are added. Tokens not consumed remain available for later arcs in the path. A path may use an arc with `forbids` only when none of those tokens are currently available.

The optional `targetConstraints` object is keyed by target body name. A target constraint may contain `maxArrival`, `maxDv`, `maxDose`, `requires`, and `forbids`. A plan reaches that requested target only when its final arrival time, cumulative costs, and final available tokens satisfy that target's constraint.

Keep a route candidate when no other candidate to the same body safely dominates it. A candidate can dominate another only when it has arrival, cumulative `dv`, and cumulative `dose` values that are each no larger, with at least one strict improvement or a strictly better usable token inventory. Token inventories are compared as sets of currently available token names. Equal token sets are interchangeable for dominance. A strict token superset may dominate an otherwise equal or better candidate when the extra tokens are useful for future `requires` checks and are not forbidden by any remaining arc or target constraint reachable from that body. A strict token subset never dominates an otherwise equal candidate that still carries additional tokens, because those tokens may be required later. Conversely, a strict token superset must not dominate an otherwise equal clean candidate when an extra token could violate a future `forbids` check.

For example, two labels at `Mars` with the same arrival, `dv`, and `dose` where one has `{assist}` and the other has `{}` should keep only `{assist}` if all later token checks are `requires`-style. If the later graph has an arc or target that forbids `assist`, both labels must remain. If one label has `{assist}` and another has `{assist,permit}`, the `{assist}` label cannot prune `{assist,permit}`; the larger inventory may unlock a later `requires: ["permit"]` leg. If a token has been consumed earlier, it is absent from the inventory used for this comparison. If two candidates tie on numeric dimensions and token inventory but have different body paths, keep both.

For requested targets, output one frontier row per non-dominated plan as `{ "target": name, "arrival": number, "dv": number, "dose": number, "path": [...] }`. Sort rows by target, then `dv`, arrival, dose, and path text.
