# sentiment-transformer / sentiment-infer — Release Dossier

_Internal engineering record. Long-form narrative with normative appendices. Read for meaning; do not skim._

## 0. Executive Summary

This dossier is the single source of truth for cutting the release of the
`sentiment-transformer` text-classification model that ships inside the
`sentiment-infer` inference crate. Three artifacts describe the same release
and they contradict one another: this dossier, the MLflow export
(`/app/sources/mlflow-export.yaml`), and the crate's own configuration
(`/app/crate/Cargo.toml` and `/app/crate/serving.toml`). Where they disagree,
this dossier wins.

A preliminary integration plan once circulated internally and is reproduced
here only as historical context. The preliminary plan had proposed to lift
every serving ceiling verbatim from the MLflow export, to keep telemetry
compiled into the shipping binary, and to serve the bf16 weights carried over
from the GPU experiment. Every one of those choices was later reversed. Do not
treat any statement in the early chapters as binding.

How to read this dossier: it accumulates decisions over time, and every
binding decision carries a date. For any one parameter, several dated values
may appear in different places, and the one bearing the latest DATE governs —
the position of a statement in this document is not a reliable guide to its
recency. A later-dated decision is often written earlier in these pages than an
older one, so do not assume the last figure you happen to read is the current
one; compare the dates. Earlier-dated and undated figures are superseded. A
baseline set of decisions was consolidated on 2026-05-18; several of those
baseline values were adjusted by later dated decisions recorded in the
narrative that follows, and it is those latest-dated values that actually ship.
The word "resolved" throughout this document means the value that stands after
the latest-dated decision for that parameter has been applied.

A further caution: parameters are usually referred to by what they do, not by
their field name. The number of requests kept in flight at once is the serving
concurrency; the largest number of inputs folded into a single forward pass is
the batch size; how long a single request may run before it is aborted is the
request timeout; the number of warmup passes each replica runs before it takes
traffic is the deployment descriptor's warmup count; the number of seconds a
draining replica is given before it is force-killed is the shutdown grace; and
the share of production traffic the first rollout stage receives is the canary
percent. The baseline section and Appendix D name each parameter and give this
gloss; the later dated adjustments use the operational phrasing instead, so
matching them up requires reading for meaning rather than searching for the
field name.

## Preliminary Integration Plan (HISTORICAL — SUPERSEDED, DO NOT IMPLEMENT)

The notes in this chapter predate the incidents and are retained only so that
reviewers can trace how the thinking changed. None of the values here are
binding. The preliminary plan asserted that the maximum batch size would be
thirty-two, copied straight from the experiment tracker, and that the maximum
concurrency would be eight to match the tracker as well. It further asserted
that the request timeout would be two thousand milliseconds and that telemetry
would remain enabled for the first two weeks of the rollout. It assumed the
accuracy gate would simply equal the measured evaluation accuracy, and that the
latency ceiling would simply equal the crate's declared maximum. It also
assumed the release version would be the crate package version verbatim. Each
of these assumptions was later reversed; see the Consolidated Normative
Decisions for the values that actually ship.

## Baseline Resolved Decisions (consolidated 2026-05-18)

The following are the baseline decisions as consolidated on 2026-05-18. They
override anything stated earlier than this date, in this dossier, in the MLflow
export, or in the crate configuration. They are the starting point the release
plan encodes — but several of the numeric ceilings and gates below were revised
after the June 2026 load rehearsal, and those later dated revisions take
precedence over the baseline values here. Apply the baseline first, then apply
every later dated revision.

### Model identity

The shipping model name is always the tracker's registered model name, never
the Cargo package name. The crate is named `sentiment-infer` for historical
reasons, but the model that ships is `sentiment-transformer`; the model name
is taken from the MLflow export.

The release version is not the crate's package version. The entire 4.3.x
crate line was yanked after the hotfix regression, so the crate's own package
version must not appear in the release plan. Instead the release train pins
the major and minor components from the MLflow model version and appends the
crate's patch component. Concretely: take the MLflow model version's major and
minor, then append a dot and the crate package version's patch number.

### Run identifier

The run identifier recorded inside the MLflow export was re-tagged during the
rollback and is stale; it must not be propagated into the release plan. The
authoritative run identifier is the one published in Appendix R (Release
Manifest), and only that value may be emitted.

### Quantization mode

This release serves on the CPU path only, and the CPU path is certified for
eight-bit integer weights. The `bf16` mode still present in `serving.toml` is
a leftover from the abandoned GPU trial and is non-authoritative. The emitted
quantization mode is the eight-bit integer mode, written exactly as `int8`.
In the release plan `quantization` is a single top-level scalar string. The
`[quantization]` table shape used inside `serving.toml` is a crate-local
convention only and must not be mirrored: the release plan never nests a
`mode` key under `quantization`.

### Feature set

Begin from the crate's `default` feature list in `Cargo.toml`. Then apply, in
order: production builds must never ship the `telemetry` feature (data
retention policy P-114 forbids it); the `dynamic-batching` feature is retained
only when the resolved serving concurrency ceiling is at least sixteen, and is
dropped otherwise; the `gpu-cuda` feature is never enabled on the CPU serving
path even if the export advertises it; exactly one quantization feature may be
present and it must agree with the resolved quantization mode, so
`quantized-int8` is kept and any `quantized-bf16` entry is removed. A further
rule applies: the `experimental-simd` feature, which is not part of the crate
default list, is added to the release feature set if and only if the resolved
maximum batch size is an exact power of two, and is left out otherwise. After
all of the above, the emitted feature list is deduplicated and sorted in
ascending lexicographic order.

### Evaluation metrics and thresholds

The evaluation metrics for this release come from
`/app/sources/metrics-history.csv`, not from the MLflow export — the export's
metrics are stale. That file is RFC-4180 CSV with the header
`run_id,timestamp,eval_accuracy,max_eval_latency_ms,notes`, and quoted fields
may themselves contain commas. A row is well-formed only if, once parsed as
RFC-4180, it has exactly five fields, a non-empty run_id, and numeric
eval_accuracy and max_eval_latency_ms values; every other row and every blank
line is ignored. Each timestamp is ISO-8601 carrying an explicit UTC offset,
and timestamps must be compared as instants in UTC (not by their local
wall-clock text). Among the well-formed rows whose run_id equals the
authoritative run identifier, select the one with the latest UTC instant. From
that selected row the accuracy gate (`min_accuracy`) is its eval_accuracy
written to exactly three decimal places, and the latency ceiling
(`max_latency_ms`) is its max_eval_latency_ms multiplied by 1.2 and then
rounded up to the next whole millisecond.

### Evaluation provenance

`model.evaluated_at` is the timestamp of that same selected row, normalized to
UTC and written in the form `YYYY-MM-DDThh:mm:ssZ` — a double-quoted string,
seconds precision, a trailing `Z`, and no numeric offset.

### Serving limits (baseline — all three were adjusted later)

At baseline the crate's declared serving ceilings are hard caps. The maximum
serving concurrency (`max_concurrency`) — the number of requests kept in flight
at once — is the crate's declared value. The maximum batch size
(`max_batch_size`) — the largest number of inputs folded into a single forward
pass — is the smaller of the export's value and the crate's value. The request
timeout (`request_timeout_ms`) — how long a single request may run before it is
aborted — is the smaller of the export's value and the crate's declared value.
Each of these three baseline values was superseded by a later dated decision
recorded elsewhere in this document, expressed in the operational phrasing
above rather than by field name; apply the latest dated value for each. The
release plan additionally records a `queue_capacity` equal to the resolved
maximum batch size multiplied by the resolved maximum concurrency, and the
feature rules likewise use the resolved concurrency and resolved batch size.

## Appendix O — Output Contract (Normative)

The release plan must be written to `/app/release-plan.yaml` as block-style
YAML with two-space indentation. The top-level keys appear in exactly this
order and no other keys are permitted: `apiVersion`, `kind`, `model`,
`quantization`, `features`, `thresholds`, `serving`.

- `apiVersion` is the literal string `release.mlops/v1`.
- `kind` is the literal string `ReleasePlan`.
- `model` is a mapping whose keys appear in this order: `name`, `version`,
  `run_id`, `evaluated_at`. The `evaluated_at` value is a double-quoted UTC
  timestamp string of the form `YYYY-MM-DDThh:mm:ssZ`.
- `quantization` is a plain top-level scalar string (for example `int8`). It
  is never a mapping and never carries a nested `mode` key.
- `features` is a block sequence, one entry per line, deduplicated and sorted
  in ascending lexicographic order.
- `thresholds` is a mapping whose keys appear in this order: `min_accuracy`,
  `max_latency_ms`. Derivations (from the selected metrics row defined in
  "Evaluation metrics and thresholds"): `min_accuracy` is that row's
  eval_accuracy with NO arithmetic adjustment, written with exactly three
  digits after the decimal point; `max_latency_ms` is that row's
  max_eval_latency_ms multiplied by 1.2 and rounded up to the next whole
  integer.
- `serving` is a mapping whose keys appear in this order: `max_batch_size`,
  `max_concurrency`, `request_timeout_ms`, `queue_capacity`, each a plain
  integer. Derivation: `queue_capacity` is exactly `max_batch_size`
  multiplied by `max_concurrency` (no additional terms). `max_batch_size`,
  `max_concurrency`, and `request_timeout_ms` are the resolved (latest-dated)
  values from the narrative.

The file ends with exactly one trailing newline and contains no trailing
whitespace on any line.

## Appendix D — Deployment Descriptor and Lockfile (Normative)

After the release plan is written, two further artifacts are produced from it
and must stay consistent with it and with each other. Every value below is
computed from the resolved plan values (that is, after all dated adjustments).

`/app/deploy.json` is a JSON object with exactly these fields:

- `replicas`: the number of serving replicas — the resolved serving
  concurrency divided by four, rounded up.
- `cpu_millicores`: 250 times the resolved maximum batch size.
- `memory_mb`: 8 times the resolved queue capacity.
- `request_deadline_ms`: equal to the resolved request timeout.
- `warmup_batches`: the resolved number of warmup passes each replica runs
  before it takes traffic (an integer; its latest-dated value is decided in
  the narrative, not here).
- `shutdown_grace_seconds`: the resolved number of seconds a draining replica
  is given before it is force-killed (an integer; latest-dated in the
  narrative).
- `canary_percent`: the resolved share of production traffic the first rollout
  stage receives, as an integer percent (latest-dated in the narrative).
- `env`: an object with exactly three string-valued keys — `QUANT_MODE` (the
  resolved quantization mode), `FEATURES` (the resolved feature list joined by
  single commas, in the same ascending order as the plan), and `MAX_INFLIGHT`
  (the resolved serving concurrency as a decimal string).

`/app/lock.json` is a JSON object with exactly these fields:

- `run_id`: the authoritative run identifier, identical to the plan's.
- `feature_count`: the number of entries in the plan's feature list.
- `replica_count`: identical to `deploy.json`'s `replicas`.
- `plan_sha256`: the SHA-256 of the exact bytes of `/app/release-plan.yaml`,
  as lowercase hexadecimal.
- `deploy_sha256`: the SHA-256 of the exact bytes of `/app/deploy.json`, as
  lowercase hexadecimal.
- `binding`: the SHA-256, lowercase hexadecimal, of the ASCII string formed by
  `plan_sha256`, a single colon, and `deploy_sha256` (in that order).

Both JSON files use two-space indentation and end with a single trailing
newline.
