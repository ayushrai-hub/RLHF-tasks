The normalized catalog is now available, but the release gate still needs to decide whether subscriber expectations are compatible with the publisher's column filters.

Extend the Kotlin CLI with `pubgate validate --catalog <json> --out <json>` while preserving the parse behavior from the previous stage. The report should compare every subscriber target table with its publication, mark compatible rows, and emit blocking diagnostics for missing publications, subscriber target tables that are absent from their referenced publication, subscriber target tables that are absent from the publisher schema, subscriber columns that are not present in the publisher schema, publication filters that omit subscriber-required columns, filters that omit primary key columns, and filtered tables using `REPLICA IDENTITY FULL`. Validation is driven from subscriber target tables; do not add extra result rows for publication tables that no subscriber targets. A table can therefore receive two `missing_table` diagnostics when it is both absent from the referenced publication and absent from the publisher schema.

Each result must use a schema-qualified `table` value like `public.accounts`, include alphabetically sorted published and subscriber column lists, and create output parent directories automatically. Diagnostics about omitted or absent columns must include a sorted `missingColumns` array. If a subscriber column is absent from the publisher schema and the publication uses a filtered column list that also omits that column, include the column in both `missing_column.missingColumns` and `unsafe_filter.missingColumns`; the later plan stage will keep schema gaps out of generated SQL. The compatibility wording is part of the checked contract: unsafe filter messages must contain `publication filter omits subscriber columns`, primary-key messages must contain `publication filter omits primary key columns`, missing publication messages must contain `not present in the publisher snapshot`, and replica-identity messages must contain `REPLICA IDENTITY FULL`. Result ordering must be deterministic by subscription, table, then publication. The exact report shape lives in `/app/docs/validation_contract.md`.
Within a single result, diagnostics must also be deterministic: missing publication/table relationship diagnostics come first, then missing publisher schema table diagnostics, then `missing_column`, `unsafe_filter`, `primary_key_omitted`, and `identity_filter_blocked` in that order when they apply. The exact report shape lives in `/app/docs/validation_contract.md`.
