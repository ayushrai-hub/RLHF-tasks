Add the apply command for the migration plan:

python3 /app/tools/msbuild_audit.py apply-plan /app/src /app/Directory.Packages.props /app/policy/runtime-policy.json /app/out/msbuild-apply-plan.json

Reuse the parsing, policy, classification, and wave behavior from the earlier milestones. The command may edit only .csproj files for projects placed in migration waves. It must leave retired, blocked, and keep projects unchanged, and must not modify /app/Directory.Packages.props, /app/policy/runtime-policy.json, source .cs files, or anything outside /app/src. Applied projects should be moved to their target TargetFramework and Nullable, including applied test projects. RuntimeIdentifiers should only be updated for non-test projects; replace singular RuntimeIdentifier with plural RuntimeIdentifiers, and remove both RID properties for test projects whose target RID list is empty. Apply the same edits when a project file uses the MSBuild XML namespace. Only update an inline PackageReference Version when that referenced package is below the effective minimum; do not add package references or inline versions for centrally managed packages.

Write applied, blocked, retire, and summary. Sort applied rows by wave then path, blocked rows by path, and retire paths alphabetically. Applied rows include path, name, wave, changes, target, and packages_updated. changes is a JSON array of changed field names using only target_framework, nullable, runtime_identifiers, package_versions in that order. packages_updated is a JSON object mapping each inline package name that was changed to the version applied, for example {"Microsoft.Extensions.Hosting": "8.0.0"}; use an empty object when no inline package versions changed. If a centrally managed project has no remaining file changes on a later run, do not include it in applied just because it still references centrally managed packages. Blocked rows include path, name, reasons, and unchanged: true, with retired dependency: <path> or dependency cycle reasons as appropriate. summary includes applied_count, blocked_count, retire_count, files_changed, package_versions_updated, and wave_count. The command must be idempotent: a second run should not report prior changes again, while still reporting blocked and retired projects.
