The variform library and command-line tool under /app/environment plan ImageMagick variant transformations from a declarative JSON spec. A spec is a list of steps, each naming a transformation method and an optional argument; the tool validates the whole spec and, when it is safe, prints the processor command it would run. Ruby is already installed and on PATH and there is no internet access, so do not try to install gems. Run it with ruby /app/environment/bin/variform check on a spec file. The behavioral contract, the supported methods, the forbidden option tokens, and the corpus layout are described in /app/environment/docs/security-spec.md, and every spec under /app/environment/testdata/valid must keep planning cleanly.

The validation layer is unsafe in more than one way. Audit the whole pipeline under lib/variform/validation and the spec normalization path that feeds it: the supported-method allow list (which still admits pass-through methods that hand the processor a raw reader target, a raw writer target, or a whole processing pipeline), the gate that matches a method against it, and the deny-list scanners that walk an argument's scalar, array, and object parts. Some unsupported methods are still accepted, some hostile method names still pass the gate, and several forbidden argument forms still reach the planned command through gaps in how argument text is scanned. Do not assume one flaw per file, that every file holds the same count, or that the plain reading of a check is its only fault. The specs under /app/environment/testdata/exploits each surface one live weakness, and the number of fixes is yours to determine from the contract.

Find and fix every flaw without breaking any well-formed spec. A hostile spec must be refused through the normal error path: exit non-zero with a short stderr message that leads with the subsystem name transform and names what was wrong, an unsupported method, a forbidden option, or a forbidden indirection. A crash, an uncaught exception, or a Ruby backtrace while handling any spec means the flaw is still live. Do not special-case fixture names or exact byte sequences, and keep each fix in the file that owns the flaw rather than in the command-line driver.

After patching, write a short security_notes.md at /app/environment/security_notes.md with one bullet per fix that names the subsystem file it lives in, describes the weakness, gives its CWE class (these option injections fall under CWE-77 command injection and CWE-94 code injection), and cites the MIT-licensed inspiration.
