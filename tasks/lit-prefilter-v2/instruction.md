A Go project in `/app` reproduces one internal step of a text-search engine: turning a set of candidate literal strings, pulled from the front of a pattern, into the final "prefilter" literal set the engine will actually scan for. Given such a set, it must produce exactly the set the reference engine settles on. The program reads one case per line from a file, `<case-id> <seq-json>`, and prints `<case-id> <optimized-seq-json>`, one line per case. Build it with `cd /app && go build -o /app/litpre .` and run it as `/app/litpre <cases-file>`.

A set of literals is encoded as compact JSON. A finite set is `{"finite":true,"lits":[{"b":[104,105],"exact":true}, ...]}`, where each literal's `b` is its bytes (integers 0..255) and `exact` says whether the literal is complete (`true`) or is only a prefix fragment that could be extended (`false`); the literals are listed in preference order, highest preference first. The special value `{"finite":false}` means the engine has decided no literal set is worth scanning for (a prefilter cannot help). Everything except the decision is already provided and must not be changed: `main.go` (the CLI), `parse.go` (the JSON encoding, which also drops a literal identical to the one just before it), and `litpre.go` (the `Literal`/`Seq` types, the fixed byte-rarity table `rank`, and the mechanical primitives — preference minimization, longest-common-prefix, first-byte trimming, dedup, the "poisonous literal" test, and the size/exactness helpers). Your job is to implement the `Optimize` method in `/app/optimize.go`; only that file may change.

The reference does not simply keep the set, nor blindly collapse it to its common prefix. It decides — based on how many literals there are, how long and how discriminating their shared prefix is, whether the set is small and complete, and how common the bytes involved are — when to shrink the set toward a single fast substring, when to trim every literal, and when to give up and scan for nothing; and if shrinking makes the set worse than the complete set it started from, it keeps the original instead. The precise conditions and thresholds are not written down here. Reconstruct them from the worked `input → reference output` pairs in `/app/examples`, which are drawn from the same engine, so that your output matches the reference on any set of this kind.
