The repository within the /app/environment directory contains a small Go CLI application named ostore. This application rebuilds the offline ingest artifacts from a local object-store directory. To start with the local deterministic workflow:
```bash
cd /app/environment
make build
make replay-smoke
```
The make replay-smoke target creates a crash and retry store, then executes the sanity check that exists in the application today. Currently, this smoke test only verifies that the payloads named in the manifest can be opened. Failures are seen in cases of attempting to publish the filesystem contents when the receipt is not committed, when attempting to use a receipt that is committed but does not match the contents of the payloads or checksum sidecars, or if the output bundles that are generated are invalid in any way. Any fixes to the Go source code or build files within the /app/environment directory are acceptable; changes outside of that directory are not. The main outputs of the CLI are the manifest, checksum-report, and provenance JSON files, all located in the /app/output directory. These files can be validated independently by deleting them, creating additional local store roots, and executing the rebuild with each local store root and output directory, then inspecting the resulting filesystem. The identifiers that are included in these files are those of the offline-object-store and the ostore-manifest-v1. All digest values are lowercase hexadecimal content digests calculated with the standard checksum primitive already used by the codebase.

A store root contains the payloads at the objects/<batch_id> paths, the checksum sidecars of the same files next to the payloads in the same directory with the sidecar extension used by the existing store code, and the receipt files at the receipts/<batch_id>.receipt.json paths. Each batch may only be published with a receipt file that contains the schema version 1, that the batch_id field matches the name of the receipt file, that the phase field has a value of committed, that it contains an integer epoch field, and that it has an objects array within the receipt. Receipt files with another phase entirely are entirely ignored by the rebuild process. Payloads that are without a committed receipt or that are not listed in any committed receipt are ignored.

For every object listed in a committed receipt file, the relative_path of that object is used to locate its payload files and checksum sidecar files. A committed object's relative_path must remain under objects/<batch_id>/ for the batch named by that receipt, so path traversal entries or paths under another batch's prefix are invalid input. The size field in the committed receipt is expected to equal the actual payload byte length. The receipt's payload digest value is the lowercase digest of the payload file contents, the sidecar digest value is obtained from the sidecar file of the same payload, and the two digest values for that payload are expected to be identical. Any receipt that uses uppercase characters for a payload digest is invalid input. Any committed receipt that is malformed, does not conform to the supported schema, uses an invalid relative_path, or has object metadata that does not match the payload or sidecar files will cause the rebuild process to exit with a non-zero exit status. On these committed-receipt validation failures, existing manifest, checksum-report, and provenance files in the output directory will not be replaced or altered. Ignoring receipt metadata that is invalid in non-committed receipt files will not prevent a committed receipt batch from being valid. Payloads with no data are valid. Objects with the same logical_key in different committed batches will still be separate objects in the resulting bundle.

The rebuild will write the three user-visible files, creating the output directory if it does not already exist. The manifest file is UTF-8 JSON with the schema, store identity, generator identity, commit count, object count, content root, and batches. The batches are stored in an array within the manifest, with each batch carrying its id, epoch, object count, batch digest, and objects array. Each object carries its logical key, relative path, size, and payload digest. The batches are stored in the manifest in order of their batch_id fields. The objects array contains the same object rows, with the objects listed in order of their logical_key fields. The checksum report is a UTF-8 tab-separated file with one row per object row in the manifest, sorted by batch_id then logical_key, and it includes both the payload digest and sidecar digest columns. The provenance file is JSON with schema and generator identity, deterministic input digest, file digest fields for the manifest and checksum report, commit count, object count, and content root. The file digest fields contain the digest of the bytes of those files. The input digest field contains the digest of the committed receipt rows within the store; it does not mirror the contents of the manifest file. The schema includes an entry for the deterministic input digest of the committed receipt rows and checksum sidecars, while excluding run-time metadata such as the time stamps of the run, the name and identity of the machine, the absolute paths to any temporary files that were created during the run, and the path to the root of the store. If two stores have the same contents, they will generate output bundles that are identical in size and content. The input digest material also includes the logical_key and relative_path fields of all objects that were published within committed receipt files to ensure they are listed within the metadata.

The canonical row fields for objects will determine the fields for all other data and digests of the rebuild. For each object row, the batch id, logical key, relative path, size, and payload digest fields will be concatenated together with tab separators and a newline character appended to create a string. All of the objects of a batch will be concatenated together to create the batch digest field. The content root field will be the digest of the concatenated contents of all object rows as they appear within the manifest file. The manifest and checksum-report file digest fields contain the digest of the manifest and checksum report files, respectively. The input digest field will be determined by creating an array of all the committed receipt rows that were encountered during the rebuild, with each row having the batch id, logical key, relative path, payload digest, and sidecar digest fields of the receipt’s objects concatenated together with tab separators, and the entire array having its contents concatenated together into a string. The size field is intentionally not included within the committed receipt rows. Both the manifest and checksum report files contain the size fields of their objects. The input digest will remain the same regardless of how many times the rebuild is performed on the same store. Stores without publishable batches are valid: their output bundle is based on no committed receipt rows, the manifest contains no batches, the content digest is based on no object rows, and the checksum report contains only its header.
