# Catalog feed importer: contract

The importer at `/app/import.js` ingests upstream product feeds into PostgreSQL.
This document is the behavioural contract: the inputs, the database it must
produce, and the command-line surface. It does not describe the on-the-wire
layout of the feeds, which is upstream-proprietary and undocumented (see "Feeds"
below).

## Database

PostgreSQL is on `127.0.0.1:5433`, database `app`, role `app` / `apppass`.

```
products(
  id    integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku   text    NOT NULL,
  name  text    NOT NULL,
  qty   integer NOT NULL,
  price numeric NOT NULL
)

import_runs(
  feed_key   text    PRIMARY KEY,
  row_count  integer NOT NULL DEFAULT 0,
  finished   boolean NOT NULL DEFAULT false
)
```

Inspect with `sudo -u postgres psql -p 5433 -d app`.

## Feeds

Each feed under `/app/data` is a single binary container produced by an upstream
service. A container holds a sequence of records: the catalog feeds carry product
records `(id, sku, name, qty, price)` and the change-log feed carries edit records
`(id, version, op, sku, name, qty, price)`. The container layout is not documented
here and differs between feeds.

The price field is carried as an integer number of cents (the probe prints it under
the name `price_ct`); the `products.price` numeric column stores the value in
dollars, that is `price_ct / 100`, written with two decimal places of scale, so
`6110` cents is stored as `61.10` (not `61.1`).

A reference decoder ships at `/app/ref/catalog-probe`. It reads one container on
stdin (or as a path argument) and prints the decoded records as a JSON array, for
example:

```
/app/ref/catalog-probe /app/data/sample.bin
```

Use it to understand what a container decodes to. It is a study aid for working
out the format. The importer must decode feeds on its own (the probe is not part
of the importer and is not guaranteed to be present when the importer runs in
production), and it must keep working on feeds it has not seen, not just the
samples shipped here.

A decoded text field may be present (a string) or absent. A decoded change-log
field may likewise be absent. Absent has meaning in the rules below: an absent
field signals no value rather than an empty value.

## Command surface

- `node /app/import.js [--dry-run] <feed>`: import a catalog feed. `--dry-run`
  decodes and counts but performs no database writes. Both print
  `processed <N> rows` as the final stdout line, where `<N>` is the number of
  records the importer decoded.
- `node /app/import.js --resume-from auto|id:<n> <feed>`: resume an interrupted
  import (see Resume).
- `node /app/import.js --changelog <feed>`: fold a change-log feed (see
  Reconciliation).
- `node /app/import.js --feed-key <k> <feed>`: import a catalog feed as part of a
  coordinated fleet (see Concurrent imports).

## Memory

Production runs the importer under `NODE_OPTIONS=--max-old-space-size=64`. Feeds
can be hundreds of thousands of records, so the importer must process records as
a stream and never hold the whole decoded feed in memory at once.

## Resume

Crashed imports are retried through `/app/bin/run-importer` with
`--resume-from auto`, against a checkpoint file `/var/lib/csv-importer/.checkpoint`
whose contents are `id:<integer>` naming the last record id committed to Postgres.

- no `--resume-from`: the checkpoint is ignored; import every record.
- `--resume-from auto`: read the checkpoint; import only records whose id is
  strictly greater than that value.
- `--resume-from id:<n>`: use `<n>` literally (inclusive, so id `<n>` is imported)
  and ignore the checkpoint file.

On every import the checkpoint is rewritten once per committed batch, after that
batch's database commit resolves, naming the last id in the batch. It must never
name records Postgres has not yet committed, and it must be durably on disk before
it counts as written, so a later `--resume-from auto` never reads a torn file.

## Idempotent re-import

Re-importing the same catalog must converge rather than fail on the primary key:
a record whose id already exists updates that row. When a catalog record's `sku`
or `name` is absent, the existing Postgres value for that text column is kept; a
present value is written. `qty` and `price` are always taken from the feed. After a clean import the identity sequence behind `products.id`
must sit at the post-import maximum id, so the next operator `INSERT` without an
id returns `MAX(id) + 1`. That advance is the importer's responsibility, not a
separate job.

## Reconciliation

A change-log feed records edits over time. `op` is `put` or `del`. A product has
one record per version and the feed is shuffled, so feed order is not version
order. Folding rules:

- Take each product's versions in version order.
- A `del` is a tombstone: it removes everything before it. A product deleted and
  later `put` again starts fresh from after that tombstone.
- For a surviving product, each column takes the value from the highest-version
  `put` after the last tombstone whose cell for that column is present. An absent
  cell in a `put` leaves that column unchanged; it does not blank it.
- A product whose latest version is a `del` does not appear at all.

After `node /app/import.js --changelog <feed>`, `products` holds exactly the
reconciled set, one row per surviving product. The feed is large and the heap is
still capped, so reconcile in a single streaming pass holding only per-product
state.

## Concurrent imports

A feed may be loaded by a fleet: several importer processes started at once with
`--feed-key <k>` for the same `<k>`. Exactly one process must perform the import
and record it in `import_runs`; the others must observe that `<k>` is already
claimed and exit 0 without importing, printing `processed 0 rows`. The winner
prints `processed <N> rows` and leaves one `import_runs` row for `<k>` with
`finished` true and `row_count` equal to the number of records it imported. The
claim must be atomic: importers that start at the same instant must never both run
the import for one key, and no importer may fail because another already recorded
the run.
